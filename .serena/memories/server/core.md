# Бэкенд

Node + Express, ESM, запуск `node server/index.js`, сборки нет. Точка входа — `server/index.js`,
она же выполняет согласование состояния на старте.

## Хранилище: одно, но с двумя бэкендами

`server/lib/supabase.js` — переключатель: `DATA_BACKEND=supabase` → общая база
(Postgres/Supabase), иначе → файлы в `server/data/`. Файловый режим существует **только** ради
локального запуска и тестов; каталог в `.gitignore` и в репозиторий не входит.

**Файлы не являются вторым хранилищем и не источник истины.** Правило владельца с созвона
24.08: другого способа хранения быть не должно — ни файлов, ни SQLite, ни `localStorage`, ни
памяти процесса. Аудит `docs/AUDIT-storage-2026-08-27.md` (MR-186) прошёл по базе и перечислил
всё поимённо.

Состояние на 27.08: у 26 сторов ветка базы есть. Файл остаётся единственным хранилищем только у
`proxies.js` (заведено отдельной задачей MR-169). SQLite остался в `parserCache.js` как запасной
путь — при включённой базе кэш пишется в таблицу `parser_cache`.

**Заводишь новый стор — сразу с веткой базы.** Стор только на файлах = нарушение правила.

Обёртки `jsonStore.js`, `kvStore.js`, `tableStore.js` прячут выбор бэкенда, поэтому доменный код
о нём не знает и знать не должен.

## Воркеры живут в памяти процесса

Отсюда два следствия, которые ловят почти всех:

1. **После правки воркера или схемы бэкенд надо перезапустить** — иначе применяется старый код.
2. **Второй экземпляр на тех же данных запускать нельзя** — экземпляры дерутся за задачи.

## Рестарт НЕ убивает задачи

Актуальное поведение (проверено по коду, `docs/` местами утверждает обратное и устарел):

- `reconcileStaleTasksOnBoot()` — `server/lib/accountLocks.js` — переводит прерванные
  `running`/`queued` задачи в **паузу** с пометкой `resumeOnBoot`. Блокировки намеренно **не**
  восстанавливает: иначе аккаунт числился бы «в работе» без единого воркера.
- `resumeMarkedTasks()` — `server/lib/taskRecovery.js` — поднимает их сразу после согласования
  локов, через обычный `resumeModuleTask`, то есть с теми же проверками, что при ручном
  «Возобновить». Вызов — `server/index.js`.
- Задачи, остановленные **человеком**, не поднимаются: флаг ставится только прерванным процессом.

Историческое: раньше такие задачи помечались `stopped`, и каждый деплой убивал активную работу.
Встретишь это утверждение в `docs/DEPLOY.md`, `docs/CONTRACT-locks-lease.md`, `docs/mcp/*` — оно
устарело.

## Ядро

`server/lib/` — по файлу на понятие. Ключевые: `channelLease` («один канал — один бот»),
`accountLocks`, `accountRunner`, `actionBilling`, `accountStatus` (state machine аккаунта),
`accessGuard`/`accessGate`/`authGuard` (доступы), `auditLog`/`actionLog`.

Контракты этих подсистем зафиксированы в `docs/CONTRACT-*.md`.

## Ловушка со статусом аккаунта

Воркеры пишут `setAccountMeta(id, {status:'working'})` напрямую, в обход state machine.
`working` нормализуется в `active`, поэтому попытка перевести аккаунт в `active` штатным
переходом молча ничего не делает («active→active»). При убийстве процесса статус остаётся
`working` навсегда: интерфейс показывает «в работе», а автоматика аккаунт спокойно берёт.

## MCP

`server/mcp/` — сервер и дескрипторы модулей. Правила синхронизации схемы и языка —
`mem:conventions`; contract-тест — `mem:task_completion`.
