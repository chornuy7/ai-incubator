# CLAUDE.md — гид по проекту для Claude Code

AI-платформа массового управления Telegram-профилями (прогрев, нейрокомментинг,
нейрочатинг, парсинг каналов, автоматизации, логи, аналитика). Фронт — React/Vite,
бэкенд — Node/Express (`server/`), сессии Telegram через GramJS.

## 🔒 WORKFLOW — обязателен. Шаги не пропускаются и не меняются местами

> Этот раздел — источник правды. Читаемый пересказ на одной странице, который удобно
> держать открытым: **[docs/WORKFLOW-rules.html](./docs/WORKFLOW-rules.html)** (открывается
> двойным кликом, без сборки). Меняется правило — правятся оба файла одним коммитом.

Каждая задача проходит эту цепочку целиком:

```
Jira подключена → ссылка на задачу → pull main → своя ветка → работа (Claude + человек)
   → «тестируй» → Ai Testing → Human Testing → Done → «залей и смержи» → заливка + мерж
```

**Условий два, и статуса мало.** Наружу ничего не уходит, пока не выполнены оба:
задача в `Done` **и** человек дал команду. До этого код живёт локально: ни `git push`,
ни деплой, ни мерж. Статус `Done` человек ставит ВРУЧНУЮ, сам, после того как проверил задачу в
`Human Testing`. Ни `Ai Testing`, ни `Human Testing` допуском не являются — важен именно
переход в `Done`.

Разделение простое: **статусы до `Done` ставит Claude** (`In Progress`, `Ai Testing`,
`Human Testing`) — это его отчёт о том, где работа. **`Done` ставит только человек** — это
его решение о том, что работа принята.

Три последних статуса — реальные состояния доски `MR` (проект Myrmex), а не выдуманные
названия: `To Do → In Progress → Ai Testing → Human Testing → Done`. Claude читает их
сам через Jira; спрашивать статус у человека не нужно и нельзя.

| # | Шаг | Кто | Что ломается, если пропустить |
|---|---|---|---|
| **0** | **Подключение к Jira** | Claude | гейт `Done` держится на статусе задачи; без Jira подтвердить его нечем, и он превращается в честное слово |
| **1** | **Ссылка на задачу в Jira** | **человек даёт, Claude обязан запросить** | работа идёт мимо доски: нечему двигаться по статусам, нечего принимать, нечем подтверждать допуск |
| 2 | `npm run sync` — подтянуть `main` | Claude | работа идёт поверх устаревшего кода; конфликт всплывает через час, а не сразу |
| 3 | Новая ветка `feat/<lane>-<имя>` | Claude | правки попадают в `main` без ревью и без тестирования человеком |
| 4 | Работа (`In Progress`) | **Claude + человек** | работа превращается в монолог: правки приходят уже как приёмка, а не как участие |
| 5 | `npm test` + `npx tsc --noEmit` локально → статус **`Ai Testing`** | **человек командует** («тестируй»), Claude выполняет | проверка стартует раньше, чем человек договорил; наружу уезжает красное |
| 6 | **`Human Testing`** — переводит Claude как сигнал «готово к проверке» + комментарий с планом (для UI — запуск и воспроизведение) | Claude ставит, человек проверяет | без сигнала задача лежит непонятно в каком состоянии; без инструкции ревью уходит на поиск экрана |
| 7 | **`Done`** — переводит человек ВРУЧНУЮ | **человек** | это единственный допуск; без него шаг 8 не начинается |
| 8 | **Команда на заливку и мерж** — «залей», «мержи» | **человек** | без неё `Done` читается как «делай» — а это статус, а не распоряжение |
| 9 | Заливка (`push`, деплой) **и** мерж в `main` | Claude выполняет | наружу и в `main` уезжает непринятое |

**Правило для Claude одной строкой: пока задача не в `Done` — не заливать и не мержить,
даже если попросили. На попытку — предупредить и остановиться.**

### Шаг 0. Без Jira работа не начинается

**Подключение к Jira — условие работы, а не удобство.** Допуск к заливке — это статус
задачи (`Done`), и статусы Claude смотрит в Jira **сам**, а не спрашивает у человека. Без
подключения подтвердить его нечем, и гейт превращается в честное слово — то есть перестаёт
быть гейтом. Заодно теряются `Ai Testing` и `Human Testing`: человек перестаёт видеть, где
работа, и вынужден верить на слово вместо доски.

Поэтому: **нет подключения к Jira → работа не начинается и не продолжается.** Не «начну, а
статус уточню потом», не «сделаю пока локально». Стоп по шаблону ниже — и ждать, пока
подключение появится.

Проверка делается ПЕРВЫМ действием, до всего остального: если Jira недоступна,
синхронизация и работа уже не имеют смысла.

**Что при этом всё-таки можно** — ровно две вещи, и обе не являются работой над задачей:
разбираться с самим подключением (иначе правило запирает выход) и отвечать на вопросы по
уже существующему коду, ничего не меняя. Всё, что пишет в файлы, коммитит, заливает или
мержит, — заблокировано.

Как подключить: коннектор Atlassian в настройках claude.ai, либо `claude mcp` / `/mcp` в
интерактивной сессии. В неинтерактивной сессии авторизацию провести нельзя — там остаётся
только сообщить, что работа заблокирована.

### Шаг 1. Без ссылки на задачу работа не начинается

**Claude обязан запросить ссылку на задачу в Jira — сам, первым делом, до любой правки.**
Работы без задачи не бывает: вся цепочка держится на её статусах, и если задачи нет, то
нечему двигаться по доске, нечего принимать и нечем подтверждать допуск к заливке.

**Дать ссылку — обязанность человека.** Задачи не существует — значит её надо создать, и
до этого момента работа не начинается и не продолжается. «Сделай пока так, заведу потом»
не принимается: «потом» превращает всю цепочку в честное слово.

**Задачу за человека Claude не заводит.** Постановка — это решение о том, что вообще
делается, и принимает его человек. Claude может предложить формулировку, но создаёт
задачу человек и он же присылает ссылку.

Разрешено при этом ровно то же, что и при отключённой Jira: разговор и чтение кода, без
единой правки. Стоп по шаблону ниже.

### Шаг 2. Всегда начинать с `main`

Первое действие после шагов 0 и 1 — `npm run sync` (детали — раздел «Перед ЛЮБОЙ задачей»).
Не «посмотреть код», не «начать править». Об этом надо сообщать вслух, а не делать молча:

- **`main` отстал** → предупредить, что работа началась бы на устаревшем коде, подтянуть,
  сказать, что подтянулось;
- **`main` уже актуален** → просто сообщить, что проверил и что всё свежее.

### Шаг 3. Работа только в своей ветке

В `main` не коммитим **никогда** — ни «мелочь», ни «только документацию». Ветка заводится
до первой правки: `feat/<lane>-<имя>` (`feat/a-mcp-docs`, `feat/b-crm-filters`).
Обнаружил, что работаешь в `main`, — остановись и перенеси изменения в ветку.

### Шаг 4. Работа — совместная, а не «Claude ушёл делать»

**Это единственный шаг с двумя владельцами.** Claude пишет код, гоняет, читает файлы —
человек ведёт работу по ходу: уточняет формулировку, отменяет подход, добавляет требование,
отвечает на вопрос, который Claude решать не вправе.

Что из этого следует на практике:

- реплика человека посреди работы — **часть шага**, а не помеха ему и не повод начинать
  задачу заново: её надо принять и продолжить;
- если решение принадлежит человеку (выбор из вариантов, спорное требование, риск) —
  спросить внутри шага 4, а не выкатывать готовое и ждать разбора на приёмке;
- правки на этом шаге **не считаются провалом тестирования** и не откатывают статус:
  задача так и висит в `In Progress`, пока идёт разговор;
- `In Progress` — состояние диалога. Оно заканчивается не «когда код дописан», а когда
  человек скажет проверять (шаг 5).

### Шаг 5. Тесты — локально и только по команде

**Claude не переводит задачу в `Ai Testing` сам.** «Я дописал» не означает «пора
проверять»: человек может ещё добавлять требования или менять подход — шаг 4 идёт, пока
идёт разговор. Тестирование начинается с команды человека.

**Что считается командой:** «тестируй», «запускай тесты», «прогоняй», «проверяй».
Формулировка свободная, наличие обязательное — как и на шаге 8.

**Claude не объявляет работу готовой — это вердикт человека.** «Готово» означает, что
требование больше не изменится, а знать этого Claude не может. Он сообщает, что сделал, и
спрашивает; формулировки вида «РАБОТА ГОТОВА» — утверждение вместо вопроса, и их не бывает.

Своё сделано, команды нет — спросить и остановиться:

> **⚠️ Я СДЕЛАЛ, ЧТО ПРОСИЛИ. СЧИТАТЬ РАБОТУ ЗАКОНЧЕННОЙ И ЗАПУСКАТЬ ТЕСТЫ?**
> Готовность определяете вы: возможно, требование ещё изменится.
> Статус не меняется, пока не прозвучит «тестируй».

Дальше `npm test` и `npx tsc --noEmit` гоняются на этой машине. Красный тест = задача не
готова, и никакие «поправлю после заливки» этого не меняют. Результат прогона сообщается
числом («столько-то из стольких-то»), а не словом «прошло»: если что-то падает —
назвать, что именно.

Зелёный прогон — основание перевести задачу в **`Ai Testing`**: этот статус на доске
означает ровно «проверено машиной, ждёт человека».

### Шаг 6. `Human Testing` — сигнал «готово к проверке», ставит Claude

Как только собственная проверка закончена (тесты зелёные, `tsc` чистый), Claude **сам**
переводит задачу `Ai Testing → Human Testing`. Это не допуск себе, а **сигнал человеку**:
задача готова, можно брать в тестирование. Без него человек не знает, ждать ещё или уже
пора смотреть.

#### Перевод и комментарий — одно действие. Порядок: СНАЧАЛА комментарий

**Перевода в `Human Testing` без комментария с планом проверки не бывает — никогда, ни при
каких обстоятельствах.** Это не «хорошо бы», а часть самого перехода.

**Сначала пишется комментарий, потом двигается статус.** Порядок не произвольный: если
сделать наоборот и что-то прервётся между шагами, задача повиснет в `Human Testing` без
единого слова о том, что проверять, — а по доске она будет выглядеть готовой. Обратный
порядок такого состояния не создаёт: комментарий без перевода безвреден.

Комментарий обязан содержать, независимо от типа задачи:

- **что сделано** — коротко, по пунктам, без пересказа коммитов;
- **результат собственной проверки** — числом (сколько тестов прошло из скольких,
  `tsc` чистый), а не словом;
- **что проверять руками** — то, чего машина проверить не может;
- **на что смотреть при приёмке** — главные риски правки;
- **что понадобится для выката**, если появились новые переменные окружения или шаги.

Эталон — комментарий в MR-209
([12602](https://provotorov200.atlassian.net/browse/MR-209?focusedCommentId=12602)):
по нему можно свериться, когда непонятно, насколько подробно писать.

Статус без плана проверки бесполезен: тестировать по названию задачи нечего.

#### Задача трогала UI — комментарий обязан содержать запуск и воспроизведение

**Если задача хоть как-то связана с интерфейсом** — страница, компонент, стили, вёрстка,
админка, живая документация MCP, любое изменение, которое человек увидит глазами, —
комментарий при переводе в `Human Testing` обязан содержать:

1. **Чем запустить** — точная команда (`npm run dev`, `npm run mcp:docs`, `npm run dev:safe`),
   порт и всё, что нужно подставить (ключ, переменная окружения). Не «запустите проект».
2. **Куда идти** — конкретный адрес и путь кликов до изменённого экрана.
   Не «откройте настройки», а `http://localhost:3011/docs/mcp` → раздел Tools → карточка
   `describe_block`.
3. **Что должно произойти** — ожидаемое поведение по шагам, включая крайние случаи, ради
   которых правка делалась. Если чинили ширину — сказать, при каком размере окна смотреть;
   если зависимый список — с какими значениями он перестраивается.
4. **Как понять, что сломано** — как выглядит дефект, который чинили. Тестировщик должен
   узнать регресс, а не гадать, «так и было или нет».

Без этого проверка превращается в поиск экрана: человек тратит ревью на то, чтобы найти,
где вообще смотреть, и до самой проверки не доходит. Правило распространяется и на правки,
где UI задет косвенно, — если увидеть результат можно только глазами, инструкция нужна.

`Ai Testing` и `Human Testing` допуском к заливке НЕ являются — ни тот, ни другой.
Допуск даёт `Done` (шаг 7), а запускает действие команда человека (шаг 8).

### Шаг 7→9. `Done` открывает вопрос, команда человека открывает действие

**Пока задача не переведена в `Done` вручную человеком, наружу не уходит ничего:**
ни `git push` в удалённую ветку, ни деплой на сервер, ни мерж в `main`. Всё это шаг 9,
и открывает его именно переход в `Done`, а не прохождение `Human Testing`.

**Увидев `Done`, Claude НЕ начинает заливку.** Действие выполняется только после команды
человека — прямого распоряжения, написанного словами.

**Что считается командой** (формулировка свободная, наличие обязательное):

| | Достаточно сказать |
|---|---|
| заливка | «залей», «запушь», «выкатывай», «деплой» |
| мерж | «мержи», «смержи в `main`», «вливай в `main`» |
| и то и то | «залей и смержи», «разрешаю заливку и мерж» |
| **не команда** | «задача в done», «готово», «ок», молчание, сам статус в Jira |

Молчание разрешением не считается, `Done` сам по себе командой не является, а разрешение
на заливку не является разрешением на мерж: это два отдельных вопроса и два отдельных ответа.

**Инициатива на этом шаге — у человека, и иначе быть не может.** Claude не сторожит доску и
не может начать разговор: между ответами он не запущен. О переводе в `Done` он узнаёт не в
момент перевода, а когда человек к нему обратится. Поэтому «Claude спросит, когда задача
попадёт в `Done`» — неверно: спросить он может только в ответ на сообщение. Если человек
написал, задача уже в `Done`, а команды в сообщении нет — вот тогда Claude сверяет статус,
задаёт вопрос по шаблону ниже (отдельным абзацем, заглавными и жирным) и останавливается.

Причина разделения простая: `Done` означает «работа принята», а не «выкатывай прямо
сейчас». Момент выката человек выбирает сам — он может зависеть от чего угодно, о чём
Claude не знает.

Просят раньше — не выполнять, предупредить по шаблону и дождаться ответа. Это не
формальность: заливка и мерж — единственные шаги цепочки, после которых откат стоит
дороже, чем ожидание.

### Шаблоны уведомлений

Все предупреждения и вопросы по workflow оформляются одинаково: **отдельным абзацем,
жирным, ключевая строка заглавными** — чтобы их нельзя было пролистать.

Запрос разрешения (человек написал, задача в `Done`, команды в сообщении нет):

> **⚠️ ЗАДАЧА `<KEY>` В `DONE`. РАЗРЕШАЕШЬ ЗАЛИВКУ И МЕРЖ `feat/<имя>` → `main`?**
> **НИ ЗАЛИВКА, НИ МЕРЖ НЕ БУДУТ ВЫПОЛНЕНЫ БЕЗ ЯВНОГО ПОДТВЕРЖДЕНИЯ.**

Попытка залить до `Done`:

> **⛔ СТОП: ЗАЛИВКА ДО СТАТУСА `DONE` НАРУШАЕТ WORKFLOW И НЕБЕЗОПАСНА.**
> **ЗАДАЧА `<KEY>` В СТАТУСЕ `<текущий>` — ЗАЛИВКА НЕ ВЫПОЛНЕНА.**
> Что дальше: провести `Human Testing`, перевести задачу в `Done` вручную, затем повторить
> запрос.

Попытка мержить до `Done`:

> **⛔ СТОП: МЕРЖ ДО СТАТУСА `DONE` НАРУШАЕТ WORKFLOW.**
> **ЗАДАЧА `<KEY>` В СТАТУСЕ `<текущий>` — МЕРЖ НЕ ВЫПОЛНЕН.**

Самопроверка перед переводом в `Human Testing` (Claude проговаривает её себе, наружу
выводить не нужно): комментарий написан? запуск и путь до экрана указаны, если задача
трогала UI? результат тестов числом? Нет хотя бы одного — **перевод не делается**.

Jira не подключена (блокирует всё):

> **⛔ СТОП: JIRA НЕ ПОДКЛЮЧЕНА — РАБОТА ЗАБЛОКИРОВАНА.**
> **БЕЗ ДОСТУПА К СТАТУСУ ЗАДАЧИ ГЕЙТ `DONE` НЕПРОВЕРЯЕМ.**
> Что дальше: подключить коннектор Atlassian (настройки claude.ai либо `/mcp` в
> интерактивной сессии) и повторить запрос. До этого я не начинаю задачу.

Ссылки на задачу нет (блокирует всё):

> **⛔ СТОП: НЕТ ССЫЛКИ НА ЗАДАЧУ — РАБОТА НЕ НАЧАТА.**
> **ПРИШЛИТЕ ССЫЛКУ НА ЗАДАЧУ В JIRA. ЗАДАЧИ НЕТ — СОЗДАЙТЕ ЕЁ.**
> Что дальше: без задачи нечему двигаться по статусам и нечем подтверждать допуск.
> Задачу за вас я не завожу — постановка ваша.

`main` не подтянут:

> **⚠️ MAIN НЕ ПОДТЯНУТ — РАБОТА ПОШЛА БЫ ПОВЕРХ УСТАРЕВШЕГО КОДА.**
> Выполняю `npm run sync` перед началом.

Работа начата в `main`:

> **⛔ СТОП: ЭТО ВЕТКА `MAIN`. РАБОТА В НЕЙ ЗАПРЕЩЕНА WORKFLOW.**
> Создаю `feat/<lane>-<имя>` и переношу изменения туда.

## ⛔ Перед ЛЮБОЙ задачей — сначала синхронизация

> Это **шаг 2** цепочки из раздела «WORKFLOW» выше. Ниже — детали и причины.

**Первое действие после блокирующих шагов 0 и 1 — всегда `npm run sync`. Не «посмотреть
код», не «начать править», а сначала это.** Скрипт (`scripts/sync.mjs`) забирает свежее в двух шагах:
текущую ветку от её upstream, затем `origin/main` в текущую ветку.

```bash
npm run sync
```

Порядок именно такой не случайно: сначала догоняем свою ветку, потом вливаем общий `main` —
так конфликт всплывает СРАЗУ и на чистом дереве, а не через час работы поверх кода, который
в `main` уже переписали. В репозитории две дорожки (A и B) в одном рабочем каталоге, и
разойтись на сотню коммитов тут — вопрос пары дней.

Скрипт **останавливается на грязном дереве** и печатает, что закоммитить. Это не помеха, а
смысл: автостэш поверх чужой незакоммиченной работы разваливается ровно тогда, когда его
труднее всего разобрать. Увидел стоп — закоммить своё (или спроси владельца чужого WIP),
потом повтори. Конфликт при влитии `main` — разрешить и закоммитить ДО начала задачи.

## ⚠️ Правила работы с кодом (созвон 27.08) — обязательны

Заказчик разобрал не что мы сделали, а **как мы работаем**, и назвал прямые пуши в `main`
причиной того, что «клауд делает криво и приходится всё перепроверять». Механика простая:
две задачи стартуют от одного состояния кода; первая пушится через пять минут, вторая всё
ещё «верит» в прежний код — и на пуше разбирает чужие правки в тех же строках. «И там
начинается каша».

1. **Каждая задача — в своей ветке.** Ветка = отдельная копия проекта: сломается ветка,
   а не проект. Можно вести хоть двадцать задач, но каждая в своей.
2. **Пуш — только в свою ветку.** В `main` напрямую не пушим.
3. **Мерж в `main` — только после явного разрешения человека.** Не «агент сам проверил и
   влил». Пока не сказали «вливай» — не вливаем.
4. **Проверять локально, а не в лайве.** Ошибка, сделанная на бою, уже на бою.

Полный разбор — [docs/TZ-2026-08-27.md](./docs/TZ-2026-08-27.md) §0.

**Флаг источника данных.** `USE_LIVE_API` в api-конфиге в корне: `true` — данные тянутся с
сервера, `false` — с локального. Раньше адреса были прописаны по всему коду.

**Выбор элемента «мышкой»** во внутреннем браузере даёт в задачу ссылку на элемент *в файлах
кода* плюс скриншот — это резко сужает область поиска. Заказчик просит пользоваться этим,
когда правка касается конкретного блока на странице.

## ⚠️ MCP — наш раздел, обязателен к синхронизации

**MCP разрабатываем мы (Lane A) целиком** — сервер, дескрипторы, транспорт. Из него растёт
отдельный сервис, поэтому у схемы один хозяин. Раздел: **[docs/mcp/](./docs/mcp/README.md)**.

**Правило для ЛЮБОЙ дорожки:** добавил или изменил поле, которое сохраняется в `task.settings`
(или завёл новый модуль) — **внеси его в дескриптор модуля тем же коммитом**.
Contract-тест (`server/__tests__/mcpDescriptors.test.js`) сверяет поля, читаемые воркером,
со схемой; рассинхрон = красный тест = PR не мержится. UI-only поля (поиск, сортировка,
фильтры отображения) не регистрируются. Формат — [MCP-SPEC.md](./docs/mcp/MCP-SPEC.md),
процедура — [MCP-CONTRIBUTING.md](./docs/mcp/MCP-CONTRIBUTING.md).

Причина жёсткости: манифест обещал «мозгам» 5 полей на модуль при реальных 32 — из-за этого
у заказчика встала разработка оркестратора.

### 🇬🇧 ЯЗЫК MCP — ТОЛЬКО АНГЛИЙСКИЙ. Правило без исключений.

**Всё содержимое MCP пишется по-английски** — и это относится к любому агенту и любой
дорожке, которые к нему прикоснутся:

- дескрипторы (`server/mcp/descriptors/`): `title`, `whoAmI` целиком, `blocks`,
  `params` (`title`, `purpose`, `constraints`, `enum.label`, `enum.means`), `presets`, `examples`;
- инструменты, промпты и ресурсы (`tools.js`, `prompts.js`, `server.js`): названия,
  описания, `instructions`, тексты ошибок и предупреждений валидатора;
- всё, что уезжает клиенту в `describe_module`, `list_capabilities`, `validate_task`
  и прочих ответах протокола.

**Не переводить на русский и не «возвращать как было».** Смешанный язык в одном ответе —
не косметика: модель, прочитавшая описание поля на другом языке, чем остальная схема,
начинает отвечать на нём же, а оркестратор у заказчика — англоязычный.

Комментарии в коде (`//`, `/** */`) и документация в `docs/mcp/*.md` остаются на русском:
их читают люди из команды, а не модель.

**Что под правило НЕ подпадает — пользовательские данные.** Имена пользователей и ролей,
названия целей и кампаний, тексты сообщений, ключевые слова — это то, что человек ввёл
сам. Их не переводят: `roleName: 'Администратор'` в ответе `capabilities` — правильно.
Правило про АВТОРСКИЙ текст схемы, а не про содержимое базы.

**Витринные подписи наружу не отдавать.** `MODULE_TITLES` (`'Рассылка'`) и `SECTIONS[].label`
(`'Прокси'`) — подписи для панели, они русские. В ответы MCP идёт английский `title`
дескриптора и `targetLabelEn`, а раздел клиент получает ключом (`/panel/proxies`), а не
подписью. Ошибиться тут легко: обе карты лежат рядом и называются похоже.

Проверяется машинно: `server/__tests__/mcpDescriptors.test.js` → тест
«язык описаний единый». Кириллица в полях, уезжающих клиенту, = красный тест = PR не мержится.

## Направление архитектуры (меняется — делать аккуратно)

- Явная **state machine** статусов аккаунта: `Active/Warming/Pause/FloodWait/Quarantine/SpamBlock/Reauth/Invalid`.
- **Блокировки → lease** («один канал — один бот», приоритет прогрева, аудит переноса).

- **Адаптер платформы** (Telegram/Instagram) — Telegram-специфику не тащить в общий слой.
- Не ломать существующее: многое уже есть (см. ROADMAP → «Что уже реализовано»).

## Память и навигация по коду

- **codebase-memory-mcp** — граф кода (tree-sitter) для быстрой навигации по большой кодовой базе.
  Ставит каждый разработчик у себя (автоконфигурит Claude Code через `.mcp.json`). Команды установки:
  ```bash
  # Linux/macOS
  curl -fsSL https://raw.githubusercontent.com/DeusData/codebase-memory-mcp/main/install.sh | bash
  # + опциональный 3D-UI графа на localhost:9749
  curl -fsSL https://raw.githubusercontent.com/DeusData/codebase-memory-mcp/main/install.sh | bash -s -- --ui
  ```
  ```powershell
  # Windows (PowerShell)
  Invoke-WebRequest -Uri https://raw.githubusercontent.com/DeusData/codebase-memory-mcp/main/install.ps1 -OutFile install.ps1
  Unblock-File .\install.ps1; .\install.ps1
  ```
  > Это удалённый install-скрипт — запускает его **человек** осознанно, Claude его не выполняет.
  > После установки перезапустить Claude Code и сказать «Index this project».
- **Файловая память Claude** (`.claude/.../memory/`) — фиксировать решения, договорённости и контракты между дорожками.
