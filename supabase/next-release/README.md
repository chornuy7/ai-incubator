# Что применяется СЛЕДУЮЩИМ выпуском, а не этим

Файлы в этой папке — готовые миграции, которые **нельзя** класть в
`supabase/migrations/` сейчас. Раннер (`server/scripts/migrate.mjs`) читает только
`supabase/migrations/*.sql` и в подпапки не заходит, поэтому здесь они лежат безопасно:
их не применит ни деплой, ни `npm run migrate`.

## Почему снос колонок нельзя выкатывать вместе с их заменой

Порядок выката такой: **сначала применяются миграции, потом деплоится код.** Между этими
двумя моментами на сервере работает ПРЕДЫДУЩАЯ версия приложения — уже с новой схемой.

Если снести старую колонку тем же выпуском, что и завести новую, в это окно предыдущая
версия обращается к колонке, которой уже нет. Окно короткое (минуты), но это минуты, в
которые панель управляет живыми Telegram-аккаунтами: воркеры продолжают работать, права
продолжают проверяться, деньги продолжают списываться.

**Одно исключение, и оно осознанное.** `2026-09-02-mr290-time-types.sql` меняет тип колонок
на `timestamptz` НА МЕСТЕ: у колонки один тип, писать «и в новое, и в старое» физически
некуда. Двойников `*_ts` для 26 колонок заводить не стали — это двойная запись в каждом
сторе и второй такой же переезд через выпуск ради окна в несколько минут. Вместо этого
выкат MR-290 идёт при ОСТАНОВЛЕННОМ сервисе (порядок — в `docs/DEPLOY.md`), и окна не
возникает вовсе. Останавливать сервис там всё равно приходится: задачи модулей переносятся
скриптом, а при живых воркерах перенос выйдет с обрывом.

Поэтому переезд всегда идёт в два выпуска:

| | Выпуск N (MR-290) | Выпуск N+1 |
|---|---|---|
| Схема | новые колонки и таблицы заведены и заполнены | старые колонки снесены |
| Код | читает новое, пишет **и новое, и старое** | пишет только новое |
| Предыдущая версия кода | продолжает работать по старому | её уже нет |

## Порядок действий для выпуска N+1

1. **Убедиться, что выпуск N отработал** — панель живёт на новой схеме хотя бы сутки, а
   не «выкатили час назад».
2. **Снять дублирующую запись в коде.** Места помечены в исходниках словами
   «пока пишется» и «Уберём вместе с колонкой»:
   `server/channels.js`, `server/goals.js`, `server/agents.js`, `server/campaigns.js`,
   `server/roles.js`, `server/users.js`, `server/accountActivity.js`,
   `server/priceStore.js`.
3. **Перенести файлы отсюда в `supabase/migrations/`** и выкатить обычным порядком.

Шаги 2 и 3 идут ОДНИМ выпуском: код, который пишет в снесённую колонку, упадёт на первой
же записи.

## Отдельно: секреты

`2026-09-03-mr290-drop-secrets.sql` сносит `proxies.password` и ключ `twoFA` из
`accounts_meta.data` — открытые пароли. Его нельзя применять, пока на проде не отработали
скрипты переноса (`encrypt-secrets.mjs`, `encrypt-proxy-passwords.mjs`, см.
`docs/DEPLOY.md`). Иначе пароли будут не перенесены, а потеряны: облачный пароль 2FA
неоткуда восстановить.

Этот файл выделен отдельно намеренно — у него условие не «прошёл выпуск», а «человек
запустил перенос и проверил результат».
