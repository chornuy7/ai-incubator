# DECISIONS · Открытые вопросы §6 (решения заказчика, 15.07)

> Единый источник решений по «заблокированным» пунктам §6 ТЗ — чтобы разработчики кодили
> из одного места, а не из скринов чата. Вся бизнес-логика продублирована в **Help Center**
> (`src/shared/config/helpDocs.ts`) и в коде (`server/lib/safetyLimits.js`).
> Статусы в [ROADMAP.md](../ROADMAP.md). Числа — стартовые дефолты, тюнятся по практике.

## 1. Trust score / авто-стоп (§3.3)

**Решение:** полную формулу пока НЕ строим. Достаточно: ручные уровни + **жёсткий авто-стоп**
по «твёрдым» сигналам (это почти есть в `accountRunner`):
- `spamblock` / `quarantine` → аккаунт в работу не берётся;
- **3 FloodWait подряд** → карантин;
- `invalid` / `reauth` → блокируется.

Полный trust score (взвешенный) — **следующий шаг**, чтобы не переписывать дважды:
- FloodWait за 24ч — 40% · история spamblock/quarantine — 25% · действия без блока — 15% ·
  возраст/GGR — 20%.
- Пороги (стартовые): `<40` → авто-стоп + прогрев; `>70` → назад в пул; `40–70` → только
  Консервативный режим.

Код: `server/lib/safetyLimits.js#AUTOSTOP`. Help Center: «Авто-стоп и здоровье аккаунта».

## 2. Лимиты безопасности (§6) — Telegram-safe дефолты

На **1 аккаунт в сутки**:

| Действие | Лимит/сутки | Риск |
|---|---|---|
| Комментарии | 20–40 | средний |
| ЛС незнакомым | 20–30 | 🔴 высокий |
| Вступления в группы/каналы | ≤ 20 | 🔴 высокий |
| Реакции | 100–200 | низкий |

Паузы между действиями: реакции/просмотры 40–180с; сообщения/комментарии 60–300с;
рассылка ЛС 90–300с. Умножаются на уровень защиты (×1.8 / ×1 / ×0.75).

Код: `server/lib/safetyLimits.js` (`DAILY_LIMITS`, `PAUSE_RANGES`). Help Center: «Лимиты
безопасности». **Осталось:** ввести суточный счётчик действий на аккаунт (сейчас лимиты
per-task) — enforcement по суткам отдельным шагом.

## 3. Мейлинг + резолв номеров (§8.4/§8.5)

**Рекомендация:** НЕ включать «слепую» массовую рассылку ЛС незнакомым — быстрый путь к бану,
нарушение ToS, жалобы. Решение о факте рассылки — **бизнесовое, на стороне заказчика**.

Если включаем — только: прогретые аккаунты (`active`, trust > 70), релевантная аудитория
(не рандом), ≤ 20–30 ЛС/аккаунт·сутки, паузы 90–300с, возможность отписки.
- Источники номеров: ручной / CSV / результат парсинга — поддержать все три.
- Нет в Telegram → пропускать (лог `skipped`).
- Текст: шаблон **или** ИИ-генерация к цели (переиспользуем Цели/KB).
- Стек: Node-модуль в этом проекте (не Yii2/PHP).

Код: `server/modules/workers.js#runMailing` (каркас, реальная отправка — на live с явным «да»).
Help Center: «Мейлинг: правила и риски».

## 4. Прогрев — действия по дням (§8.2)

Уровни: Быстрый (2д, ~40/день, ×0.8) / Нормальный (3–7д, ~20/день, ×1.3) /
Стандартный (7–14д, ~10/день, ×2.0). Активность **растёт по дням** (не плоско).
Пропорция действий: просмотр постов 40% · реакции 20% · чтение/открытие ЛС 20% ·
вступления 10% · подписки 10%. Окна: 9:00–23:00, ночью пауза.

Код: `server/lib/workerLoop.js#warmingPace`. Help Center: «Политика прогрева».

## 5. Капча/антиспам (§8.6)

3 стратегии: `auto` (кнопка/математика — сам) · `operator` (картинка/кастомный вопрос —
флаг оператору, не обходим) · `skip` (не распознана — выходим). Игровые/эмодзи — 1 попытка
авто, иначе оператор. Собственные проверки Telegram (SMS/reCAPTCHA) — **не автоматизируем**.

Код: `server/lib/captcha.js#classifyCaptcha`. Help Center: «Капча и антиспам в группах».
