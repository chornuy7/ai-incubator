# Часть 1. Техническое задание

## 1. Цель

Привести систему к понятному и стабильному состоянию, чтобы её можно было передать первому пользователю. Для этого необходимо:

- исправить блокирующие ошибки;
- унифицировать интерфейс и структуру модулей;
- привести терминологию к одному виду;
- сделать запуск и результат работы прозрачными;
- внедрить понятный процесс Human Testing в Jira;
- после UI-исправлений реализовать полное логирование действий аккаунтов.

## 2. Jira и процесс работы

### 2.1. Workflow

Основной поток задачи:

`To Do → In Progress → Human Testing → Done`

- При каждом возврате из Human Testing в In Progress обязательно добавлять комментарий с причиной возврата и описанием найденной проблемы.
- Для визуальной задачи должен быть приложен финальный скриншот результата.
- Скриншот прикладывает разработчик до закрытия либо система добавляет его автоматически после анализа UI-задачи.

### 2.2. Labels

- Использовать labels типа задачи: `UI`, `UX`, `Backend`.
- Для задач этого созвона использовать `tz0608`.
- Не создавать labels для приоритета: для этого используется системное поле Priority.
- Удалить дублирующие labels `high`, `medium`, `low` и другие метки приоритета.
- Провести аудит непонятных и дублирующих labels.
- `help` — Help Center, `support` — поддержка.

## 3. Общие правила интерфейса

### 3.1. Единая структура модулей

Общие блоки должны иметь одинаковые названия, порядок, внешний вид и поведение:

1. Выбор аккаунтов.
2. Настройки.
3. Промпты или уникальные параметры модуля.
4. Группы/каналы.
5. Тайминги и задержки.
6. Нижняя панель запуска.

Внутри блока «Настройки» первой строкой всегда идёт «Защита аккаунтов», затем уникальные настройки модуля.

Уникальные блоки допускаются, если они действительно нужны конкретному модулю. Одинаковые блоки необходимо реализовать как самостоятельные переиспользуемые компоненты, не привязанные к одной странице.

### 3.2. Терминология

- Не использовать сленг.
- Одинаковые сущности везде называть одинаково.
- Ссылки на модуль должны использовать официальное название модуля.
- «Папки» и «Цели», если это одна сущность, переименовать в «Группы».
- «Пресет» переименовать в «Шаблон».
- «Окно постов» заменить на «Сколько последних постов обрабатывать».
- «Начать прогрев», «Создать рассылку» и другие варианты запуска заменить на «Начать».
- Удалить «Семантический фильтр к цели» и «Релевантность поста к цели».
- Стоп-слова и ключевые слова разделять точкой с запятой; рядом показать инструкцию.

### 3.3. Обязательные и необязательные блоки

- В навигаторе сначала показывать обязательные блоки, затем необязательные.
- Не смешивать обязательные и необязательные пункты.
- В обучении явно отмечать, какой шаг обязателен, а какой опционален.

## 4. Нижняя панель запуска

Панель должна быть компактной и не занимать значительную часть экрана.

До запуска показывать:

- количество выбранных аккаунтов;
- количество групп/каналов;
- лимиты;
- расчётную стоимость;
- приблизительное время выполнения;
- выбор и сохранение шаблона;
- кнопку «Начать».

Рекомендуемая компоновка по решению созвона:

- шаблон — слева;
- параметры, расчёты и навигация — по центру;
- кнопка «Начать» — справа.

Внутренний раздел должен называться «Параметры и лимиты», а не «Запуск». Отдельный блок со статистикой удалить после переноса данных в нижнюю панель.

## 5. Регистрация и защита запросов

### 5.1. Форма регистрации

- Поля: полное имя, email, пароль, повтор пароля.
- Поле «Имя» переименовать в «Полное имя».
- Полное имя: минимум 4 символа.
- Email должен иметь корректный формат и быть уникальным.
- Имя не обязано быть уникальным.
- Пароль: минимум 6 символов.
- Пароль и повтор пароля должны совпадать.
- Убрать автозаполнение формы.
- Ошибки Supabase/API выводить в интерфейсе, а не только в Network или Console.
- Для повторного email показывать понятное сообщение о существующем аккаунте.

Финальный список разрешённых символов полного имени требует отдельного подтверждения.

### 5.2. Защита

- Изучить и включить доступные в Supabase ограничения по IP и flood.
- Защита должна применяться не только к регистрации, но и к запросам, идущим в БД через Supabase API.

## 6. Account Manager и выбор аккаунтов

### 6.1. Статусы и даты

- Сохранять результат Spam Block после обновления страницы.
- Показывать дату добавления аккаунта.
- Показывать дату последней проверки Spam Block.
- Показывать дату последней проверки Proxy.
- Добавить действие «Обновить статус».

### 6.2. Единый компонент выбора

- Использовать один полноширинный компонент во всех модулях.
- Не дублировать счётчик: показывать одно значение в формате «2 из 50».
- Убрать заголовки группировки по странам из списка аккаунтов.
- Фильтрация по стране остаётся через dropdown «Все страны».
- Можно сохранять сортировку, но без разделителей «Украина», «Польша» и других заголовков внутри списка.

### 6.3. Нерабочие аккаунты и Proxy

- Аккаунт с нерабочим Proxy нельзя предлагать для запуска задач.
- Нерабочие аккаунты автоматически исключаются из обычных списков выбора.
- В header добавить колокольчик с уведомлением о количестве отвалившихся аккаунтов/Proxy.
- Убрать действие «Скрыть рабочие».
- Добавить нижнюю раскрывающуюся панель «Показать нерабочие (N)».
- Нерабочие аккаунты по умолчанию скрыты в этой панели.
- Поиск по ID должен находить нерабочий аккаунт, даже когда панель закрыта.

## 7. Dashboard задач

Для каждой задачи показывать:

- автора запуска;
- дату и время создания;
- приблизительное время выполнения;
- текущий статус;
- действия Play/Resume, Pause и Stop.

Информация должна быть доступна в общем списке и Dashboard задач. Приблизительное время также показывается в нижней панели до запуска.

Название задачи обсуждалось как возможное улучшение, но было отложено и не входит в обязательный scope.

## 8. Help Center и подсказки

- Знак вопроса всегда располагать справа от элемента и не менять его позицию.
- Удалить дублирующий маленький знак вопроса рядом с «Защитой аккаунтов».
- Маленькие подсказки у отдельных режимов, например «Сбалансированный», оставить.
- Удалить избыточную плашку `AI` внутри AI-модуля.
- Убрать дублирующее раскрываемое вниз описание «Как работает защита».
- Знак вопроса и текстовая ссылка «Как работает защита» должны открывать нужную статью Help Center в боковой панели.
- Подсказка настройки должна открывать соответствующий раздел, а не общий раздел защиты аккаунтов.

## 9. AI Prompts

- Исправить ложную ошибку `Failed to fetch`, которая появляется после успешного сохранения глобального системного промпта.
- В «Активном промпте» показывать полный итоговый текст, включая глобальный системный промпт.
- Формулировку «По умолчанию» пока оставить без изменений.

## 10. Шаблоны

- Шаблон сохраняет настройки модуля и распределения.
- Выбранные аккаунты в шаблон не входят.
- Владелец по умолчанию — текущий пользователь.
- Владельца можно выбрать только среди подключённых пользователей.
- Выбор и сохранение шаблона доступны без прокрутки: в начале модуля или в нижней панели.
- В каждом модуле должен быть выбор шаблона.
- Создать менеджер шаблонов: просмотр, применение, редактирование и удаление.

## 11. Тайминги и задержки

- Основное состояние содержит три крупных режима: минимум, сбалансированный, максимум.
- Для каждого режима показать короткое объяснение.
- Посекундные параметры убрать в раскрываемый блок «Продвинутые настройки».
- Блок оформить по примеру «Защиты аккаунтов».

## 12. Группы, каналы и Blacklist

- Использовать единый компонент выбора групп.
- «Папки» переименовать в «Группы».
- «Прошлые задачи» должны позволять повторно использовать группы/каналы из прошлых запусков.
- В Blacklist можно добавить отдельный канал или целую группу.
- В блоке целевых каналов счётчик размещать до отметки «Обязательно».

Окончательное решение о наличии Blacklist во всех модулях требует унификации: блок должен либо использоваться одинаково, либо различие должно быть объяснено.

## 13. Нейрокомментинг

- Использовать общие компоненты аккаунтов, настроек, групп, таймингов и запуска.
- Удалить устаревший блок «Кампании и цели».
- Перенести статистику запуска в нижнюю панель.
- Режимы постов: «Только новые», «Только существующие», «Все посты».
- «Все посты» означает новые и существующие.
- Выбор типа постов не должен исчезать или становиться непонятным при переключении режима.
- Для ключевых слов использовать разделитель «точка с запятой» и показать инструкцию.

### 13.1. Распределение типов комментариев

- Общая сумма всегда 100%.
- Заблокированные значения не меняются.
- Изменение незаблокированного значения не должно сбрасывать всю форму или равномерно перераспределять уже введённые значения.
- Перераспределение происходит только за счёт доступных незаблокированных значений.

Точный порядок, из какого поля вычитать процент первым, на созвоне не утверждён и требует отдельного решения.

## 14. Массовые реакции

- Сделать выбор режима визуально заметным.
- Удалить сломанный элемент справа в настройках.
- «Цели» переименовать в «Группы».
- Режим «Мониторинг новых постов» показывает выбор групп.
- Режим «Реакции на существующие посты» показывает список ссылок на посты.
- Для двух режимов использовать только согласованные названия.
- Текущий набор emoji пока оставить без изменений.

## 15. Прогрев аккаунтов

- Перенести «Уровень прогрева» из запуска в настройки или отдельный блок.
- Убрать внутреннюю кнопку запуска из блока.
- «Начать прогрев» переименовать в «Начать».
- Цена, количество аккаунтов, шаги и запуск должны выглядеть так же, как в остальных модулях.

## 16. Нейродиалоги

- Разделить «Настройки» и «AI-автоответы/Промпты».
- В настройках первой показывать «Защиту аккаунтов».
- Удалить Preview из модуля.
- Историю действий перенести в Account Manager.
- Переработать механику «Целевое действие / Фиксировано».

Новая логика завершения диалога не утверждена. Сначала требуется UX/discovery-задача.

## 17. Mailing

- Полностью перестроить модуль по общей структуре.
- Выбор аккаунтов сделать полноширинным.
- Получателей, темы и безопасность разнести по понятным блокам настроек и групп.
- «Создать рассылку» заменить на «Начать».

## 18. Autoposting

- Полностью перестроить модуль по тем же правилам, что Mailing.
- После публикации сохранять аккаунт, группу, ссылку на пост, дату, время и текст.

## 19. Mass Looking

- Упростить выбор количества последних элементов.
- Добавить понятные числовые варианты и произвольное значение.
- Привести аккаунты, группы, настройки и запуск к общему виду.

## 20. AI Rating

- Если модуль не завершён и не протестирован, временно скрыть его.
- Исправить появление второго/дублирующего баланса.
- Текущая карточка рейтинга показывает неполную информацию и требует доработки перед открытием.
- Пакетное ценообразование «за 10 аккаунтов» отложено и не входит в ближайший scope.

## 21. Лендинг и обучение

### 21.1. Галерея модуля

- Изображение занимает не больше трети экрана; ориентир по высоте — около 350 px.
- По клику или Zoom изображение открывается полноэкранно.
- Использовать скриншоты отдельных блоков, а не всей страницы с меню.
- Под изображением показывать ленту миниатюр.
- При переключении меняются активный номер, название блока и короткое описание его назначения.

### 21.2. Документация

- Обновлять обучение последним, после стабилизации интерфейса.
- Описывать элементы сверху вниз и слева направо.
- Использовать простой язык без необходимости додумывать смысл.
- Для каждого блока показывать отдельный скриншот и объяснение.
- Явно отмечать обязательные и опциональные шаги.
- Непонятное описание верхнего навигатора и шагов запуска переписать.

## 22. Полное логирование действий — следующий большой этап

Система должна сохранять каждое действие:

- тип: пост, комментарий, реакция или чат;
- аккаунт;
- группа/канал;
- ссылка на объект;
- дата и время;
- текст или значение действия;
- связанная задача/запуск;
- доступные ответы и реакцию аудитории.

В Account Manager для каждого аккаунта необходимо показывать:

- все посты;
- все комментарии;
- все реакции;
- все чаты;
- группы, в которые он вступил;
- фильтры по типу действия, группе и периоду.

Сохранённые ссылки на собственные посты должны использоваться модулем массовых реакций без повторного поиска и ручного ввода URL.

## 23. Не входит в ближайший scope

- Парсинг остальных данных — после текущих исправлений.
- Расширение списка emoji.
- Пакетное ценообразование AI Rating.
- Расширенная аналитика текстов и эффективности до внедрения логирования.
- Название задачи при запуске.

## 24. Требует уточнения

1. Финальный список допустимых символов полного имени.
2. Точный алгоритм перераспределения незаблокированных процентов.
3. Новая механика «Целевое действие / Фиксировано».
4. Должен ли Blacklist присутствовать во всех модулях.
5. Финальные labels `UI/UX/Backend` желательно проверить по текущей Jira из-за неточного распознавания этой фразы в записи.

# Часть 2. Roadmap

## Этап 0. Jira и QA-процесс

**Результат:** настроены workflow, комментарии возврата, скриншоты UI и понятные labels.

- JR-001 — workflow Human Testing.
- JR-002 — аудит и очистка labels.
- JR-003 — правила закрытия и скриншотов.

## Этап 1. Блокирующие исправления

**Результат:** регистрация валидируется, статусы аккаунтов сохраняются, опасные аккаунты исключены из запусков.

- AUTH-001 — полная валидация регистрации.
- AUTH-002 — защита Supabase API.
- AM-001 — статусы и даты проверок.
- AM-002 — исключение аккаунтов с нерабочим Proxy.
- AM-003 — панель и поиск нерабочих аккаунтов.
- NOTIFY-001 — уведомления об отвалившихся аккаунтах.
- PROMPT-001 — сохранение и полный AI Prompt.

## Этап 2. Общие UI-компоненты

**Результат:** общие элементы выглядят и работают одинаково.

- UI-001 — нижняя панель и ETA.
- UI-002 — структура модулей.
- UI-003 — выбор аккаунтов.
- UI-004 — группы и Blacklist.
- UI-005 — тайминги и Advanced Settings.
- UI-006 — терминология.
- HELP-001 — Help Center и подсказки.
- TPL-001 — сохранение и применение шаблонов.
- TPL-002 — менеджер шаблонов.

## Этап 3. Dashboard задач

**Результат:** видно, кто и когда запустил задачу, сколько она займёт и как ею управлять.

- TASK-001 — автор, время, ETA, Play/Resume, Pause, Stop.

## Этап 4. Исправления модулей

Порядок после готовности общих компонентов:

1. NC-001 — Нейрокомментинг.
2. REACT-001 — массовые реакции.
3. WARM-001 — прогрев аккаунтов.
4. ND-001 — Нейродиалоги.
5. MAIL-001 — Mailing.
6. POST-001 — Autoposting.
7. LOOK-001 — Mass Looking.
8. RATING-001 — AI Rating.

Каждый модуль отдельно проходит Human Testing.

## Этап 5. Лендинг и обучение

**Результат:** документация соответствует стабилизированному интерфейсу.

- LAND-001 — галерея блоков.
- LEARN-001 — обновление документации после UI.

## Этап 6. Полное логирование

**Результат:** каждое действие аккаунта сохраняется и доступно в Account Manager.

- LOG-001 — модель данных действий.
- LOG-002 — запись действий модулей.
- LOG-003 — история аккаунта.
- LOG-004 — сохранённые посты для массовых реакций.

## Этап 7. Отложенный backlog

- REACT-002 — расширение emoji.
- LOG-005 — аналитика контента и отклика.
- PARSE-001 — дальнейший парсинг.
