## 2. Подтверждение массовых действий с аккаунтами ⬜
**Где:** верхняя панель массовых действий в «Менеджере аккаунтов» и все действия над
группой выделенных аккаунтов (≈10 действий: Включить / Пауза / Отключить / Стоп-освободить /
Переместить / В корзину / Реавторизация / Снять / смена статуса и т.п.).

**Требование (по количеству выделенных аккаунтов):**
- **≤ 10 аккаунтов** → **1 подтверждение** («Вы уверены, что хотите …?»).
- **> 10 аккаунтов** → **2 подтверждения подряд**:
  1) «Вы уверены, что хотите перевести N аккаунтов в паузу?»
  2) «Вы точно уверены? Это затронет N аккаунтов.»

**Применить ко ВСЕМ ~10 группам массовых действий** (не только «в корзину»/«отключить»,
где подтверждение уже частично есть).

**Защита от «прокликивания» (важно):**
- Два подтверждения (>10) должны быть в **РАЗНЫХ местах экрана** — чтобы нельзя было
  дважды кликнуть в одну точку и «проскочить» оба.
- Варианты: кнопка «Подтвердить» во 2-м диалоге в другом углу; ИЛИ ввод числа N
  вручную; ИЛИ смена порядка кнопок (Отмена/Подтвердить меняются местами). Цель —
  осознанное второе действие, а не автоматический двойной клик.

**Замечания к реализации:**
- Сейчас частично: «В корзину» и «Отключить(frozen)» просят 1 подтверждение при ≥2 акк.
- Нужен единый механизм: порог 10 → двойное подтверждение (в разных местах), ≤10 → одинарное, для каждого действия.
- Бизнес-логику продублировать в **Help Center** (правило заказчика: вся бизнес-логика в Help Center).

**Статус:** ⬜ TODO (по решению — реализуем позже пакетом).

## 3. Выпадающие списки (Select) «плавают» — не привязаны к кнопке ⬜
**Где:** дашборд задач (фильтры «Все цели», «Все модули», «Все статусы»), пикер аккаунтов
(фильтр «Все страны») — и, по словам тестировщика, **в других местах тоже**. Общий компонент.
**Симптом:** при открытии меню оно появляется НЕ под своей кнопкой-триггером, а «плавает»
посреди страницы поверх карточек/списка (см. скрины QA).
**Причина (вероятно):** позиционирование дропдауна (portal/absolute/fixed) не считает
координаты триггера, или неверный anchor.
**Нужно:** меню должно раскрываться ровно под своей кнопкой (или над, если не влезает),
шириной ≥ триггера, с закрытием по клику вне/Esc. Починка одного общего Select/Dropdown
чинит все места сразу.
**Приоритет:** высокий (заметно на глаз, много где).
**Статус:** ⬜ TODO.

(GGR/парсеры/масслукинг) — без подтверждения.

## 5. Распределение типов: сумма > 100% → БЛОКировать запуск (не нормировать) ⬜
**Где:** Нейрокомментинг → «Распределение типов, %».
**Сейчас:** при сумме ≠ 100% просто «нормируется при запуске» (тихо пересчитывается),
запуск разрешён даже при 102% или 1609%.
**Надо (по требованию заказчика):** сумма процентов не должна превышать 100. Если сумма
> 100% — НЕ пускать запуск, показать ошибку (напр. «Сумма типов N% > 100 — уменьшите»).
Пример: 10+10+10+10+10+10+50 = 110% → запуск заблокирован.
**РЕШЕНИЕ (заказчик):** ≤100% допускается, >100% — БЛОКировать запуск с ошибкой.
Добавить кнопку «= 100%» (авто-выравнивание типов в один клик).
**Приоритет:** средний.
**Статус:** ⬜ TODO (решено, в работу).

## 6. «Стоп» не отзывчивый: тост «Остановка…», а статус ещё «Выполняется» ⬜
**Где:** карточка задачи (детальная страница модуля + Дашборд задач), кнопка «Остановить».
**Симптом:** после клика показывается тост «Остановка…», но статус остаётся «Выполняется»
(и на детальной, и на дашборде) ещё некоторое время. Пользователь думает, что не остановилось.
**Причина:** воркер в этот момент в длинном `sleep()` (напр. «Задержка перед вступлением 146с»)
и проверяет флаг stopRequested только ПОСЛЕ пробуждения. Плюс UI не показывает промежуточное
состояние «Останавливается…».
**Надо:** 1) бэкенд — длинные sleep дробить на короткие куски с проверкой stopRequested
(стоп срабатывает за 1–2с, а не через 146с). 2) UI — сразу после клика показывать
«Останавливается…» (оптимистично), кнопку блокировать, затем «Остановлена».
**Примечание:** по факту задача ОСТАНАВЛИВАЕТСЯ (commentsSent 0, ничего не отправлено) —
это проблема отзывчивости/обратной связи, не потеря стопа.
**Живое подтверждение (QA):** прогрев на Консервативном уровне спит между действиями
до ~130с (pickDelay(30,90)×1.44). После «Остановить» статус остаётся running и АККАУНТ
ОСТАЁТСЯ ЗАЛОЧЕННЫМ всё это время (нельзя взять в другой модуль), пока воркер не проснётся.
`locks/reconcile` не помогает (воркер «живой»). → надо дробить sleep (проверять stopRequested
каждые 1–2с) + освобождать лок сразу при stopRequested.
**Приоритет:** ВЫСОКИЙ (для боевых модулей — критично: стоп должен быть мгновенным).
**Статус:** ⬜ TODO.

## 7. Шаблоны поиска: поведение при выборе НЕСКОЛЬКИХ шаблонов ❓ (уточнить)
**Где:** Парсер → шаблоны поиска (несколько сразу).
**Замечание тестировщика:** при выборе 2 шаблонов область поиска сужается — потому что
ключи ищутся «вместе» (пересечение), а не каждый шаблон отдельно. Пример: шаблон1 «IT» +
шаблон2 «Школа» → ищет «IT Школа» (узко), а хотелось бы «IT» и «Школа» по отдельности (шире).
**Надо уточнить у заказчика:** как должно работать при 2+ шаблонах —
  (а) объединение (union): результаты каждого шаблона складываются (шире); или
  (б) пересечение (AND): канал должен подходить под ВСЕ шаблоны (уже, текущее)?
  Возможно нужен переключатель «Объединять / Пересекать шаблоны».
**Примечание:** AND-пересечение по ключевым СЛОВАМ уже есть (тумблер), вопрос про ШАБЛОНЫ.
**РЕШЕНИЕ (заказчик):** нужен ПЕРЕСЕЧЕНИЕ (AND) — канал должен подходить под ВСЕ шаблоны
(меньше результатов, точнее: напр. и IT, и Школа). Union НЕ нужен. Уточняется только:
делать ли переключатель Перетин/Объединение (по умолч. перетин) — ждём финальный ответ X/Y.
**РЕШЕНИЕ финал (заказчик):** вариант Y — переключатель «Пересечение / Объединение»,
по умолчанию ПЕРЕСЕЧЕНИЕ (AND). Реализуем.
**Статус:** ⬜ TODO (в работу).

лимиты действий/на аккаунт, диапазоны).

в основном по модулям). Касается всех модулей («и так везде»).
**Объём:** большой (контент по всем блокам всех модулей) — пакетно.
