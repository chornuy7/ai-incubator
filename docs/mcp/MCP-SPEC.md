# MCP — спецификация дескриптора (формат v1)

Технический контракт раздела. Всё, что описывает модуль, живёт в **одном** файле-дескрипторе
на модуль: `server/mcp/descriptors/<module-key>.js`. Из него собираются MCP-инструменты,
help-ресурсы, `inputSchema`, серверная валидация и (в перспективе) UI-схема.

Правило нулевого уровня: **дескриптор — источник правды.** Если поле есть в воркере, но нет
в дескрипторе — падает contract-тест (см. §7), PR не мержится.

---

## 1. Структура дескриптора

> **Язык дескриптора — английский, всегда.** Все строки, уезжающие клиенту (`title`,
> `whoAmI`, `blocks`, `params`, `presets`, `examples`), пишутся по-английски и не
> переводятся на русский ни при каких правках. Русский остаётся в комментариях кода и в
> этих markdown-файлах. Проверяется тестом «язык описаний единый»; правило целиком —
> в [CLAUDE.md](../../CLAUDE.md).

```js
export default {
  key: 'neuro-commenting',           // ключ модуля, совпадает с MODULE_DEFS
  version: 1,                        // версия схемы модуля; растёт при несовместимой правке
  usesAi: true,                      // §1.1 — зовёт ли модуль модель. ОБЯЗАТЕЛЬНО, boolean
  title: 'Нейрокомментинг',
  platform: 'telegram',              // какую платформу драйвит модуль
  tags: ['comments', 'ai', 'channels', 'engagement'],   // ключевые слова поиска; уникальны, нижний регистр

  whoAmI: { ... },                   // §2 — «кто я», строго про ЭТОТ модуль
  blocks: [ ... ],                   // §3 — функциональные блоки
  params: [ ... ],                   // §4 — плоский список параметров, каждый привязан к блоку
  presets: [ ... ],                  // §5 — расшифровка пресетов/перечислений
  examples: [ ... ],                 // §6 — сценарии использования целиком
}
```

### 1.1. `usesAi` — тратит ли модуль токены модели

Обязательное булево поле. У него два потребителя, и оба ломаются молча:

- **`server/priceStore.js`** читает его прямо из дескрипторов
  (`USES_AI = new Set(Object.values(DESCRIPTORS).filter((d) => d.usesAi)…)`) и по нему решает,
  начислять ли модулю месячный пакет токенов. Дескриптор здесь — источник правды для цен.
- **«Мозги»** по нему понимают, добавится ли к цене действия расход на генерацию.
  У ИИ-модулей `estimate_task` и `capabilities` дополнительно отдают `tokenUsd`,
  `tokenUsdModel` и `imageMultiplier`; у остальных этих полей нет вовсе.

Писать `undefined` (не объявлять поле) нельзя: «не знаю» неотличимо от «нет», а цена
считается по «нет». Contract-тест требует именно `boolean` — это уже случалось: пять
парсеров передавали флаг в фабрику, фабрика его не читала, и наружу уезжал `undefined`.

Поле выходит наружу через `describeModule`, `summarizeModule`, `list_modules`,
`describe_module` и карточку модуля в `capabilities`. Добавить его в дескриптор и не
вывести — тот же рассинхрон, ради лечения которого заведён раздел.

> **Курса `coinsPer1kTokens` больше нет.** Он был признан выдуманным значением и удалён из
> модели цен (созвон 19.08). Из ответов MCP он тоже убран — обещать «мозгам» величину,
> которой в системе не существует, ровно так же вредно, как обещать несуществующее поле.

## 2. `whoAmI` — самоописание модуля

Заменяет глобальное «about me», которое заказчик отверг. Отвечает на вопрос «что делает
**этот** модуль», а не «что за платформа».

```js
whoAmI: {
  summary: 'Пишет ИИ-комментарии под новыми постами публичных каналов от имени управляемых аккаунтов.',
  does: [
    'подписывается на канал и его группу обсуждения, если аккаунт ещё не подписан',
    'выбирает пост по правилу режима комментирования',
    'генерирует текст комментария моделью с учётом цели и базы знаний',
    'публикует комментарий и фиксирует результат в логах задачи',
  ],
  doesNot: [
    'не пишет в личные сообщения (это модуль «Мейлинг» / «Нейродиалоги»)',
    'не постит в собственные каналы (это «Автопостинг»)',
  ],
  requires: ['минимум один прогретый аккаунт с рабочим прокси', 'минимум один канал-цель'],
  risks: 'Реальное действие в Telegram. Ошибка настроек = FloodWait, спамблок, потеря аккаунта.',
  costModel: 'Списывается за действие по прайсу модуля; текст ИИ включён в цену действия.',
}
```

Обязательны все шесть полей. `doesNot` — не формальность: без него оркестратор регулярно
выбирает не тот модуль.

## 3. `blocks` — функциональные блоки

Блок — это то, что человек видит как секцию интерфейса, а «мозги» должны понимать как
смысловую группу. Закрывает требование «какому блоку относится параметр» и слой «Помощь».

```js
{
  id: 'accounts',
  title: 'Выберите аккаунты',
  purpose: 'Какими управляемыми аккаунтами выполняется задача.',
  howItWorks: 'Аккаунты разбирают действия между собой; занятый другой задачей аккаунт '
            + 'не выдаётся (один аккаунт = одна задача). Непрогретые, в карантине и без '
            + 'рабочего прокси — недоступны.',
  api: { method: 'POST', path: '/api/modules/neuro-commenting/tasks', fills: ['accountIds'] },
  params: ['accountIds'],
}
```

Поле `api` обязательно и отвечает ровно на вопрос заказчика: «какой API он использует
и какие параметры в этом API он заполняет».

## 4. `params` — параметры

Один элемент = одно поле, которое **уходит в БД задачи**. UI-only поля (поиск, фильтры
списка, сортировка) в дескриптор не попадают.

```js
{
  name: 'maxComments',
  block: 'limits',
  title: 'Макс. комментариев',
  type: 'integer',                       // string | integer | number | boolean | array | object
  required: false,
  default: 100,
  min: 1, max: 100000,                   // → JSON Schema minimum/maximum
  unit: 'комментариев',
  purpose: 'Верхняя граница числа комментариев за всю задачу. Задача завершится по достижении.',
  constraints: [
    'должен быть ≥ minComments, иначе запуск отклоняется («Минимум больше максимума»)',
  ],
  examples: [10, 100, 500],
  storedAs: 'task.settings.maxComments',
  seeAlso: ['minComments', 'maxPerAccount'],
}
```

Для перечислений — обязательны `enum` **с расшифровкой значения**, а не только подписью:

```js
{
  name: 'commentMode',
  block: 'modes',
  title: 'Режим комментирования',
  type: 'integer',
  enum: [
    { value: 0, label: 'Случайный',          means: 'Из окна последних постов берётся один случайный.' },
    { value: 1, label: 'По ключевым словам', means: 'Комментируются только посты, содержащие keywords.' },
    { value: 2, label: 'Все посты',          means: 'Комментируется каждый подходящий пост окна.' },
  ],
  default: 0,
}
```

Типы правил в `constraints` пишем человеческим текстом и **обязательно** дублируем машинно
там, где это выразимо в JSON Schema (`pattern`, `minLength`, `minimum`, …). Текст — для
объяснения, схема — для проверки.

## 5. `presets` — расшифровка пресетов

Требование заказчика дословно: пресет обязан объяснять, что он физически делает.

```js
{
  param: 'delayPreset',
  title: 'Пресет темпа',
  values: [
    { value: 0, label: 'Агрессивный',    multiplier: 0.6,
      means: 'Паузы ×0.6 (чаще), длительность ×0.75. Быстрее, но выше шанс FloodWait и ограничений.',
      useWhen: 'прогретые «расходные» аккаунты' },
    { value: 1, label: 'Сбалансированный', multiplier: 1,
      means: 'Базовые задержки. Рекомендуемый режим повседневной работы.' },
    { value: 2, label: 'Консервативный', multiplier: 1.8,
      means: 'Паузы ×1.8 (реже), длительность ×1.5. Медленнее, минимум риска бана.',
      useWhen: 'новые и дорогие аккаунты' },
    { value: 3, label: 'Custom', multiplier: 1,
      means: 'Задержки берутся как введены, без масштабирования. Только в этом режиме поля разблокированы.' },
  ],
  source: 'server/lib/protection.js (PRESET_MUL) — множители сервера и UI обязаны совпадать',
}
```

`source` обязателен: он делает утверждение проверяемым и не даёт документации разъехаться
с кодом молча.

## 6. `examples` — сценарии

Полный валидный запуск целиком, а не поле по отдельности. Это то, с чего «мозги» начинают.

```js
{
  title: 'Мягкий прогон по 3 каналам',
  when: 'нужно аккуратно проверить связку аккаунт+прокси на живом канале',
  input: {
    accountIds: ['acc_1'], channels: ['@durov'],
    commentMode: 0, maxComments: 5, maxPerAccount: 5,
    delayPreset: 2, aiProtection: true, protectionLevel: 0,
  },
}
```

## 7. Contract-тест (то, что не даёт схеме соврать)

`server/__tests__/mcpDescriptors.test.js` — обязательный:

1. **Полнота.** Каждый ключ, который читает воркер модуля и `validateSettings`, присутствует
   в `params`. Новое поле без дескриптора → красный тест.
2. **Обратное направление.** Каждый `param` реально читается кодом. Мёртвых полей в схеме нет.
3. **Целостность.** Все `params[].block` существуют в `blocks`; все `blocks[].params`
   существуют в `params`; enum-значения уникальны; `min ≤ default ≤ max`.
4. **Совпадение чисел.** Множители пресетов в дескрипторе равны константам сервера.
5. **Обязательные поля описания.** `whoAmI` заполнен полностью, у каждого параметра непустые
   `purpose` и `title`.

Именно этот тест — техническая гарантия под требованием заказчика. Без него «схема
соответствует реальности» держится на дисциплине, а дисциплина всегда отказывает.

## 8. Транспорт и инструменты MCP — ☑ реализовано

Сервер: JSON-RPC 2.0 поверх **Streamable HTTP**, точка входа **`POST /api/v1/mcp`**,
авторизация `Authorization: Bearer <api-key>` (тот же ключ, что у `/api/v1`, права —
владельца ключа). Код — [`server/mcp/server.js`](../../server/mcp/server.js),
константы протокола — [`server/mcp/protocol.js`](../../server/mcp/protocol.js).

Адрес совпал с манифестом намеренно: `GET` остался за старым REST-срезом, которым уже
пользуются, `POST` — вход протокола. Ломать существующий URL ради красоты не стали.

### 8.1. Две эры протокола на одном эндпоинте

Ревизия **2026-07-28** перестроила основу MCP: рукопожатия больше нет, сессий нет,
каждый запрос сам несёт версию и возможности клиента. Ревизии `2025-11-25` и раньше,
наоборот, требуют `initialize`. Спецификация прямо разрешает обслуживать обе эры на
одном адресе (§ Backward Compatibility), и мы это делаем: ломать уже подключённых
legacy-клиентов нельзя, а новым нужен современный протокол.

| | **modern** (`2026-07-28`) | **legacy** (`2025-11-25` … `2024-11-05`) |
|---|---|---|
| Начало работы | ничего не нужно; по желанию `server/discover` | `initialize` + `notifications/initialized` |
| Версия | `params._meta["io.modelcontextprotocol/protocolVersion"]` на КАЖДОМ запросе | один раз в `initialize` |
| Возможности клиента | `_meta["io.modelcontextprotocol/clientCapabilities"]`, обязательны | один раз в `initialize` |
| Личность сервера | `_meta["io.modelcontextprotocol/serverInfo"]` в каждом результате | `serverInfo` в ответе `initialize` |
| Тип результата | `resultType: "complete"` обязателен | поля нет |
| Статусы ошибок | 400 / 404 по спецификации | 200 с телом ошибки |
| `ping` | удалён | работает |
| Сессии, `Mcp-Session-Id`, GET-поток, `Last-Event-ID` | отсутствуют | не используем и не использовали |

Эру определяем по тому, КАК клиент пришёл. Заголовок сильнее тела: если
`MCP-Protocol-Version` объявил современную версию, а `_meta` пуст — это не legacy-клиент,
а сломанный modern, и он получает внятную ошибку, а не молча обслуживается по старым
правилам.

**`server/discover` обязателен** и работает БЕЗ версии в `_meta` — иначе им нельзя было бы
узнать версии. Отдаёт `supportedVersions`, `capabilities`, `instructions` и `serverInfo`
одним запросом.

### 8.2. Методы

`server/discover`, `initialize` (legacy), `notifications/*` (202 без тела), `ping` (legacy),
`tools/list`, `tools/call`, `resources/list`, `resources/templates/list`, `resources/read`,
`prompts/list`, `prompts/get`.

Пакетные запросы не поддерживаются — они убраны из протокола; на массив отвечаем понятной
ошибкой, а не «внутренней».

### 8.3. Коды ошибок

Диапазон **−32020…−32099 спецификация забрала себе целиком**: реализация не имеет права
придумывать там свои коды. Используем только определённые:

| Код | Имя | Когда |
|---|---|---|
| `−32020` | `HeaderMismatch` | `Mcp-Method` / `Mcp-Name` / `MCP-Protocol-Version` не совпали с телом |
| `−32021` | `MissingRequiredClientCapability` | нужна возможность, которую клиент не объявил |
| `−32022` | `UnsupportedProtocolVersion` | версия не поддерживается; в `data.supported` — список, чтобы клиент повторил запрос |
| `−32602` | Invalid params | в т.ч. **ресурс не найден** — код `−32002` в 2026-07-28 запрещён |

Коды из этого диапазона всегда едут со своим HTTP-статусом, даже если запрос выглядел
legacy: раз мы их вернули, значит говорим на современном протоколе. `UnsupportedProtocolVersion`
на статусе 200 — худший из возможных ответов: клиент решит, что мы legacy, вместо того
чтобы повторить запрос с версией из `supported`.

**Ошибка инструмента ≠ ошибка протокола.** Неописанный модуль, невалидная задача, занятый
аккаунт → `isError: true` с текстом: модель это читает и исправляется. Неизвестное ИМЯ
инструмента и нарушения самого JSON-RPC → коды −32600/−32601/−32602: их модель не починит.

### 8.4. Требования транспорта, которые сервер обязан соблюдать

Сверено с текстом спецификации 2026-07-28 (Transports → Streamable HTTP, Authorization):

| Требование спецификации | Как выполнено |
|---|---|
| `Origin` **MUST** проверяться (защита от DNS rebinding) | белый список хостов, расширяется через `MCP_ALLOWED_ORIGINS`; запрос без `Origin` (curl, сервер-к-серверу) пропускается — атака возможна только из браузера. Тело отказа — JSON-RPC ошибка без `id`, как разрешает спецификация |
| `server/discover` **MUST** быть реализован | реализован, работает в обеих эрах |
| Заголовки `Mcp-Method` / `Mcp-Name` **MUST** совпадать с телом | сверяем, при расхождении −32020 + 400; `Mcp-Name` понимает sentinel-кодировку `=?base64?…?=`. **Наличия** заголовков по умолчанию не требуем — см. ниже |
| Неизвестный `MCP-Protocol-Version` → **400** + `UnsupportedProtocolVersionError` | на POST и GET; заголовка нет — считаем `2025-03-26`, как велит раздел совместимости |
| Неизвестный метод → **404** + `−32601` | по статусу клиент отличает нас от legacy-сервера без MCP-эндпоинта |
| Списки **MUST** нести `ttlMs` и `cacheScope` (`CacheableResult`) | `tools/list`, `resources/list`, `resources/templates/list`, `resources/read`, `prompts/list`, `server/discover`; `cacheScope: "private"` — состав зависит от ключа, общий кэш на прокси отдал бы одному тенанту схему другого |
| Результаты **MUST** нести `resultType` | `"complete"` на всех modern-ответах; legacy-клиенту поле не отправляем — он его не знает |
| Списки **SHOULD** поддерживать пагинацию | `tools/list` и `resources/list` отдают `nextCursor`; 107 ресурсов одной страницей не приезжают |
| Инструменты **SHOULD** идти в детерминированном порядке | порядок массива `TOOLS` фиксирован — это даёт клиенту кэшировать список и попадать в prompt-кэш модели |
| Уведомление или ответ клиента → **202** без тела | оба случая отвечают 202 |
| GET на MCP-эндпоинт: `text/event-stream` **или 405** | поток не держим → GET с `Accept: text/event-stream` получает **405**; обычный GET по тому же адресу отдаёт REST-манифест |
| DELETE (завершение сессии) → **405** | сессии убраны из протокола; 405 с пояснением |
| Битое тело → `−32700` | обработчик стоит сразу за `express.json()`: раньше клиент получал HTML-страницу express, которую не разбирает |
| 401 **MUST** нести `WWW-Authenticate` с `resource_metadata` | RFC 6750 + RFC 9728; см. §8.5 |
| Пакетные запросы убраны из протокола | массив отвергается понятной ошибкой |
| Сообщения **MUST** быть в UTF-8 | проверено на боевом ответе — кириллица целая |

Сессии (`Mcp-Session-Id`) не используем: сервер без состояния, каждый запрос
самодостаточен. В 2026-07-28 их не существует вовсе, в прошлых ревизиях они были
необязательны.

**Одно осознанное отступление.** Спецификация называет `Mcp-Method` и `Mcp-Name`
обязательными, но ревизия свежая, и клиентские SDK их пока не шлют: безусловный отказ
выключил бы живых клиентов. По умолчанию мы проверяем **согласованность** заголовков с
телом — именно в ней и состоит защита, ради которой они введены (балансировщик
маршрутизирует по заголовку, сервер исполняет тело; разъехались — запрос посчитали не там,
где выполнили). Полная строгость включается `MCP_STRICT_HEADERS=1`; когда экосистема
догонит, флаг станет умолчанием.

### 8.5. Обнаружение авторизации (RFC 9728)

MCP-клиент, получив 401, идёт читать `resource_metadata` из заголовка `WWW-Authenticate`.
Раньше он получал голый 401 и не понимал ничего: ни какой это ресурс, ни в чём ошибка —
текст в теле написан для человека.

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="murmex", error="invalid_token",
                  error_description="The API key is unknown, revoked or malformed.",
                  resource_metadata="https://<host>/.well-known/oauth-protected-resource/api/v1/mcp"
```

Документ метаданных публичный (он нужен ровно тем, у кого токена ещё нет) и отдаётся с
корня, а не из-под `/api/v1`: RFC 9728 задаёт путь от origin. Канонический URI берётся из
`PUBLIC_BASE_URL`, иначе собирается из `X-Forwarded-*` — за прокси внутренний адрес в
документ попасть не должен. Код — [`server/mcp/wellKnown.js`](../../server/mcp/wellKnown.js).

Полноценный OAuth 2.1 у нас не развёрнут: ключ выдаётся вне протокола. Поэтому
`authorization_servers` в документе **отсутствует**, пока не задан `MCP_AUTHORIZATION_SERVERS`.
Обещать клиенту OAuth-поток, которого нет, хуже, чем не обещать ничего: он потратит раунд
discovery и упрётся в 404.

**`resource_policy_uri` → [`/docs/mcp/policy`](../../server/mcp/docs/policy.html).** Поле
означает не «как авторизоваться», а «требования ресурса к тому, КАК КЛИЕНТ МОЖЕТ
ИСПОЛЬЗОВАТЬ полученные данные» (RFC 9728 §2). Оно какое-то время указывало на раздел про
вход — это была подмена смысла: про вход отвечают `authorization_servers` и
`WWW-Authenticate`.

Страница описывает три категории того, что эндпоинт отдаёт (схема без персональных данных;
данные владельца ключа — имя, почта, роли, баланс; операционные логи с именами аккаунтов),
запреты (выгрузка вовне, обучение моделей, обогащение и профилирование получателей),
сроки хранения, и отдельно — обязательства по данным ТРЕТЬИХ ЛИЦ: мейлинг и нейродиалоги
работают с людьми, которые ни на что не соглашались, поэтому законное основание и отработка
отказов лежат на операторе, а чёрный список применяется до любого действия во всех модулях.

Политика доступна **всегда**, в отличие от самой документации: её читает клиент, только что
получивший 401, а на проде документация выключена, пока не задан `MCP_DOCS=1`. Гейта на её
маршруте нет намеренно.

### 8.6. Инструменты

| Инструмент | Назначение | `readOnly` | `destructive` |
|---|---|---|---|
| `list_capabilities` | Что этому ключу вообще доступно: модули, подсистемы, собственные права. См. §8.8 | ✔ | — |
| `describe_capability` | Одна возможность любого вида целиком | ✔ | — |
| `list_modules` | Перечислить модули с `whoAmI.summary`, тегами и признаком полноты схемы | ✔ | — |
| `describe_module` | **Главный.** Полное описание: блоки, параметры, ограничения, пресеты, примеры, `inputSchema` | ✔ | — |
| `describe_block` | Слой «Помощь»: один блок — назначение, работа, API, поля | ✔ | — |
| `validate_task` | Проверить черновик по схеме **и по правилам запуска**, без запуска | ✔ | — |
| `estimate_task` | Стоимость и время до запуска | ✔ | — |
| `get_task` | Статус, прогресс и хвост лога созданной задачи | ✔ | — |
| `stop_task` | Остановить задачу (уже сделанное не откатывается) | — | нет |
| `create_task` | Создать и запустить задачу | — | **да** |

`validate_task` отделён от `create_task` намеренно: «мозги» должны иметь возможность
собрать черновик и проверить его, не тратя деньги и не трогая аккаунты. `create_task`
вызывает ТУ ЖЕ функцию валидации — расхождение между «проверил» и «запустил» это худшее,
что можно сделать с оркестратором.

**У каждого инструмента обязателен `outputSchema`.** Без него `structuredContent` — это
JSON, про который клиент не знает ни полей, ни типов: модель гадает по одному примеру
ответа, а клиент не может провалидировать результат. Схема выхода — половина контракта.

**Аннотации обязаны быть честными.** `create_task` помечен `destructiveHint: true`:
он публикует в Telegram и списывает деньги, откатить нельзя. `destructiveHint: false`
означает для клиента «изменения только аддитивные, можно вызывать без подтверждения» —
про самый дорогой вызов набора это прямая ложь. `stop_task`, наоборот, оставлен
неразрушающим: помечать «разрушающим» аварийный тормоз значит заставить клиента
спрашивать подтверждение ровно тогда, когда нужно жать не думая.

### 8.7. Ресурсы и промпты

Ресурсы: `murmex://module/<key>` (полный дескриптор), `murmex://help/<key>/<block>` (help).
Шаблоны URI отдаются через `resources/templates/list` — клиент собирает адрес сам, не
листая каталог из 107 позиций.

Промпты — готовые рабочие процедуры, а не украшение
([`server/mcp/prompts.js`](../../server/mcp/prompts.js)): `plan_campaign`,
`configure_module`, `preflight_launch`, `diagnose_task`. Раньше возможность `prompts`
объявлялась, а список приходил пустой — обещание без содержания.


### 8.8. Возможности: четыре среза

Модуль — не единственное, чем оперирует оркестратор. Прокси, менеджер аккаунтов, дашборд
задач и статистика — отдельные подсистемы со своими правами и своими эндпоинтами. Пока
`/api/v1/capabilities` отвечал только про модули, «мозги» строили план, который упирался
в 403 на первом же шаге и выглядел как поломка сервера.

**Три вида возможностей:**

| Вид | Что это | Чем выдаётся доступ |
|---|---|---|
| `module` | кампанийный модуль: делает действия в Telegram, имеет схему задачи, стоит денег за действие | право на модуль + подписка; внутри — права на блоки `модуль:блок` |
| `service` | подсистема платформы, не являющаяся модулем: прокси, аккаунты, задачи, аналитика, своя статистика, цели, кампании, CRM, каналы, логи, автоматизация, баланс | раздел из `SECTIONS` (§8.1) |
| `user` | сам носитель прав: роли, что ему разрешено, лимиты, баланс | — |

**Четыре среза** (REST; MCP-эквиваленты справа):

| Запрос | Что отдаёт | MCP |
|---|---|---|
| `GET /api/v1/capabilities` | всё сразу: модули + подсистемы + владелец ключа | `list_capabilities()` |
| `GET /api/v1/capabilities/modules` | только модули | `list_capabilities({kind:'module'})` |
| `GET /api/v1/capabilities/services` | только подсистемы | `list_capabilities({kind:'service'})` |
| `GET /api/v1/capabilities/user` | владелец ключа | `describe_capability({kind:'user', id:'me'})` |
| `GET /api/v1/capabilities/users` | все пользователи (админ/сервис) | `list_capabilities({kind:'user'})` |
| `GET /api/v1/capabilities/<kind>/<id>` | одна возможность любого вида | `describe_capability({kind, id})` |

`<kind>` — `modules` / `services` / `users`; для пользователя `me` означает владельца ключа.

**Ключевое поле — `access`.** У каждой возможности посчитано, разрешена ли она ВЛАДЕЛЬЦУ
КЛЮЧА, и почему:

```json
{ "allowed": false, "reason": "not granted: the role does not allow section /panel/tasks" }
```

`allowed: false` — это факт о правах, а не сбой: повторять запрос бессмысленно, надо
выбрать другой путь. Это написано и в `instructions` сервера.

**Права считаются ТЕМ ЖЕ кодом, что и вход в панель** —
[`server/lib/effectivePermissions.js`](../../server/lib/effectivePermissions.js). Функция
раньше жила приватной внутри `usersRoutes.js`; при добавлении слоя возможностей её
вынесли, а не переписали рядом. Две реализации «что человеку можно» означали бы, что
панель показывает одно, а API отвечает другое, и разбираться пришлось бы уже по жалобе.

**Каталог подсистем опирается на `SECTIONS` из `roles.js`** — существующий список
областей платформы, уже привязанный к правам. Свой список «что у нас есть» рядом
заводить нельзя: он разойдётся с тем, по которому реально выдаётся доступ, и `allowed`
начнёт врать. Contract-тест это проверяет.

**Чужого пользователя** читает только админский или сервисный ключ; ключ, привязанный к
пользователю, видит ровно себя и получает 403 на остальных. Ключ, ссылающийся на
удалённого пользователя, не получает ничего (fail-closed) — иначе отозванный сотрудник
продолжал бы работать ключом.

Реестр — [`server/mcp/capabilities.js`](../../server/mcp/capabilities.js), один на REST и
на MCP: тест сверяет, что оба пути отдают идентичный объект.

### 8.9. Живая документация — `/docs/mcp`

Веб-страница, которая всё, что показывает, читает у самого сервера: инструменты со схемами
входа и ВЫХОДА, аннотации поведения, ресурсы и их шаблоны, промпты, версии протокола,
таблица кодов ошибок, возможности и дескрипторы всех модулей. Ни одного факта о протоколе
она не хранит — устареть ей нечем.

У каждого блока есть **Run**: страница отправляет настоящий JSON-RPC и показывает и
запрос (с заголовками транспорта — `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`),
и ответ сервера. Заголовки видно всегда, а не только когда они не совпали.

```bash
npm run dev        # /docs/mcp на основном порту, рабочие данные
npm run mcp:docs   # только документация: свой порт и изолированные данные
```

Второй режим нужен, потому что два экземпляра на одной папке данных несовместимы:
`reconcileStaleTasksOnBoot` при старте помечает running-задачи как `stopped`, то есть
второй запуск глушит задачи первого.

Правила доступа:

- Сама страница ключа **не требует** — иначе её нельзя было бы открыть, чтобы ключ ввести.
  Живёт вне `/api`, поэтому её не закрывает ни `sessionGuard`, ни `requireApiKey`.
- Ключ хранится в `localStorage` браузера и подставляется её скриптом в запросы к
  `/api/v1/*`, которые как были, так и остаются закрытыми.
- В панели запроса ключ **замаскирован**: панель существует, чтобы её показывали и
  скриншотили, а вместе со скриншотом уезжал бы и ключ от всего `/api/v1`.
- На проде (задан `SESSION_SECRET`) страница выключена, пока не задан `MCP_DOCS=1`:
  это инструмент разработчика, и висеть открытым на боевом домене ему незачем.

Адрес страницы отдаётся в манифесте (`GET /api/v1/mcp` → `mcp.docs`) и печатается в
консоль при старте сервера. Код — [`server/mcp/docs.js`](../../server/mcp/docs.js) и
[`server/mcp/docs/index.html`](../../server/mcp/docs/index.html).

## 9. Версионирование

- `version` дескриптора растёт при **несовместимой** правке (удалили поле, сузили диапазон,
  поменяли смысл значения enum). Добавление необязательного поля версию не двигает.
- Изменения фиксируются в `CHANGELOG` внутри [MCP-MAP.md](./MCP-MAP.md) — «мозгам» нужно
  видеть, что поменялось между их запусками.

## 10. Порядок правки

1. Меняешь поведение модуля → правишь дескриптор в **том же** коммите.
2. Гоняешь `npm test` — contract-тест ловит рассинхрон.
3. Обновляешь строку модуля в [MCP-MAP.md](./MCP-MAP.md) (покрытие/версия/дата).

Для напарника процедура расписана отдельно: [MCP-CONTRIBUTING.md](./MCP-CONTRIBUTING.md).
