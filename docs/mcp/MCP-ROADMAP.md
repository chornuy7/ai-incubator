## Этап 2 — Настоящий MCP-сервер `14.08` — ☑

**Что:** протокол вместо REST-заглушки.

- ☑ JSON-RPC 2.0 поверх Streamable HTTP — [`server/mcp/server.js`](../../server/mcp/server.js).
  Точка входа **`POST /api/v1/mcp`**, авторизация `Authorization: Bearer <api-key>`,
  права владельца ключа. GET того же адреса остался за старым манифестом — им уже пользуются.
- ☑ `initialize` (согласование версии протокола + `instructions` с порядком работы),
  `notifications/*` → 202 без тела, `ping`, `tools/list`, `tools/call`,
  `resources/list`, `resources/read`, `prompts/list`.
- ☑ Инструменты — [`server/mcp/tools.js`](../../server/mcp/tools.js): `list_modules`,
  `describe_module`, `describe_block`, `validate_task`, `estimate_task`, `create_task`.
- ☑ Ресурсы: `murmex://module/<key>` и `murmex://help/<key>/<block>` — 10 штук для
  нейрокомментинга (модуль + 9 блоков).
- ☑ Валидатор схемы — [`server/mcp/validate.js`](../../server/mcp/validate.js):
  типы, границы, enum, неизвестные поля + правила, невыразимые схемой
  (`requiredWhen`, `effectiveWhen`, `supersededBy`) — и всё это на русском, с указанием поля.
- ☑ Тесты — [`server/__tests__/mcpServer.test.js`](../../server/__tests__/mcpServer.test.js), 18 шт.
- ☑ Проверено живым HTTP: `initialize` → 2025-06-18, `tools/list` → 6 инструментов,
  `describe_module` → 9 блоков / 29 параметров, `validate_task` ловит `probability: 150`
  и отсутствующий `durationMinutes`, без ключа — 401.

**Два решения, принятых по ходу:**

1. **Ошибка инструмента ≠ ошибка протокола.** Неописанный модуль, неверные аргументы,
   невалидная задача возвращаются как `isError: true` с текстом — модель это читает и
   исправляется. Транспортные коды (-32600/-32601/-32602) остались за нарушениями JSON-RPC.
2. **`create_task` валидирует ТЕМ ЖЕ кодом, что и `validate_task`.** Расхождение между
   «проверил» и «запустил» — худшее, что можно сделать с оркестратором.

**DoD выполнен.** Клиент подключается по протоколу, получает схему, проверяет черновик
без запуска, узнаёт цену и создаёт задачу — не трогая REST.

Пять парсеров собраны двумя общими фабриками (`_parserChannels.js`, `_parserParticipants.js`):
воркеров два, ключей пять, и две копии описания на 20 параметров разошлись бы за неделю.

**Что вскрылось при сплошном покрытии** — всё это не было записано нигде:

- `deadline` читают все воркеры, кроме мейлинга и автопостинга: у этих двух дедлайн
  кампании задачу НЕ остановит;
- `maxPerAccount` не работает у нейродиалогов и прогрева — воркеры его не вызывают;
- у нейродиалогов `protectionLevel` дополнительно задаёт размер пачки ответов за заход (2/4/6);
- у мейлинга и автопостинга нет лимитов «N действий» и работы по времени: объём задачи —
  это длина списка целей;
- у AI Rating пустой список аккаунтов означает «проверить все» — единственный такой модуль;
- у снятия спамблока свои поля пауз (`delayMin`/`delayMax`) вместо общей структуры `delays`;
- поля пересечения аудиторий читает общий воркер парсеров, но применяет только
  `parsing-users` — у двух других они в схему не включены.

**DoD выполнен:** покрытие 15/15, contract-тест зелёный на каждом модуле, `list_modules`
подтверждает полноту на проде.

## Этап 4 — «Мозги» реально пишут задачи `17.08` — ◐

- ☑ **Сквозной прогон на боевом стенде через протокол:** `describe_module` → `validate_task`
  → `estimate_task` → `create_task` → `get_task`. Задача `ggr_fdbd62d4`: статус `done`,
  прогресс **5/5**, все пять аккаунтов проверены, инициатор `mcp`.
- ☑ Задача, созданная через MCP, помечается `initiator: 'mcp'` — видно и в дашборде, и в `get_task`.
- ☑ **`get_task` и `stop_task`** добавлены: без них оркестратор умел запускать и не умел
  наблюдать (`create_task` возвращал REST-путь, закрытый сессией).
- ☐ Запрет ручной правки задач «под MCP» (MR-148) — пометка есть, гейта в UI пока нет.
- ☐ Уточняющие вопросы «мозгов» до запуска (эпик MR-160).

**Что нашёл живой прогон** — три дефекта, которых не видели ни тесты, ни ревью:

1. **Задачи из API и MCP никогда не выполнялись.** `startWorker` поднимает задачу из
   хранилища по id, а оба API-пути не сохраняли её перед стартом — воркер молча выходил.
   Клиент получал `taskId` и `queued` навсегда. REST-эндпоинт вёл себя так с 27.07.
2. **Дескриптор AI Rating обещал недостижимое:** «пустой `accountIds` = проверить все».
   Ветка в воркере есть, но `validateSettings` отклоняет пустой список до неё.
   Поймал `validate_task` — именно потому, что прогоняет НАСТОЯЩУЮ проверку запуска.
3. **Знаменатель прогресса выдумывался** у модулей без лимита действий: «6/35» там, где
   проверено 6 аккаунтов из 6.

Первый пункт — тот самый класс отказа, ради которого всё затевалось: «мозги» создавали
бы задачи, которые молча не делают ничего.
