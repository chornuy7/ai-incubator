## Этап 1 — Дескриптор в коде + защита от вранья `15.08` — ☐

**Что:** карта переезжает из markdown в исполняемый код и начинает проверяться тестом.

- ☐ `server/mcp/descriptors/neuro-commenting.js` — дескриптор по [MCP-SPEC](./MCP-SPEC.md).
- ☐ `server/mcp/descriptors/index.js` — реестр + сборка `inputSchema` (JSON Schema) из `params`.
- ☐ `server/__tests__/mcpDescriptors.test.js` — **contract-тест** (SPEC §7): поле есть в
  воркере, но нет в дескрипторе → красный тест. Это то, что чинит корневую жалобу
  «ни хрена не соотносится».
- ☐ `GET /api/v1/modules/:key/describe` — полное описание модуля JSON'ом (для заказчика —
  возможность посмотреть результат курлом до готовности MCP-транспорта).
- ☐ Обновить `GET /api/v1/mcp` — собирать из дескрипторов, а не из `MODULE_DEFS`.

**DoD:** `curl .../api/v1/modules/neuro-commenting/describe` отдаёт всё, что перечислено
в требованиях §3.1 VISION. Заказчик получает **машинный** ответ, а не документ.
**Это и есть «MCP полностью заполненный для одного модуля» — с запасом к дедлайну 17.08.**

## Этап 2 — Настоящий MCP-сервер `16–17.08` — ☐

**Что:** протокол вместо REST-заглушки.

- ☐ JSON-RPC 2.0 + Streamable HTTP, точка входа `POST /mcp`, авторизация Bearer.
- ☐ `initialize`, `tools/list`, `tools/call`, `resources/list`, `resources/read`.
- ☐ Инструменты: `list_modules`, `describe_module`, `describe_block`, `validate_task`,
  `estimate_task`, `create_task`.
- ☐ Ресурсы: `murmex://module/<key>`, `murmex://help/<key>/<block>`.
- ☐ Проверка живым MCP-клиентом (подключение, `tools/list`, вызов `describe_module`).

**DoD:** «мозги» подключаются штатным MCP-клиентом и получают схему нейрокомментинга,
проверяют черновик через `validate_task` и запускают задачу — не трогая наш REST.
