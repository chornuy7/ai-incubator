# MCP — отчёт по итогам созвона 14.08.2026

**Приоритет закрыт в день постановки, на 3 дня раньше срока.**

Просили: «в течение следующих трёх дней хотя бы прислал MCP полностью заполненный,
хотя бы для одного модуля», и «по возможности сегодня — хоть что-нибудь».

Сделано 14.08: **не документ, а работающий MCP-сервер**, и **не один модуль, а три**.

---

## 1. Что было и в чём была проблема

`GET /api/v1/mcp` назывался MCP, но им не был: обычный REST-эндпоинт со списком «tools»,
подключиться к нему MCP-клиентом невозможно. И главное — он **врал о схеме**: обещал
5 полей на модуль (`accountIds`, `targets`, `maxActions`, `goalId`, `campaignId`), тогда
как нейрокомментинг реально принимает 32. Оркестратор, написанный по такому описанию,
собирал задачи, которые либо не запускались, либо работали не так, как задумано.

## 2. Что сделано

### 2.1. Настоящий MCP-сервер

```
URL:  https://myrmexgram.ai/api/v1/mcp     (POST, JSON-RPC 2.0)
Auth: Authorization: Bearer <api-key>
```

Протокол целиком: `initialize` (согласование версии + инструкция по порядку работы),
`tools/list`, `tools/call`, `resources/list`, `resources/read`, `ping`, уведомления.
Версии: `2025-06-18`, `2025-03-26`, `2024-11-05`. Подключается штатным MCP-клиентом.

**Шесть инструментов:**

| Инструмент | Что делает |
|---|---|
| `list_modules` | Все модули платформы + признак, у каких схема полная |
| `describe_module` | **Главный.** Исчерпывающее описание модуля |
| `describe_block` | Справка по блоку: что делает, как работает, какой API заполняет |
| `validate_task` | Проверка черновика задачи **без запуска и без списания денег** |
| `estimate_task` | Цена и время до запуска |
| `create_task` | Создать и запустить задачу |

Разделение намеренное: собрать черновик → проверить → узнать цену → и только потом
тратить деньги и трогать живые аккаунты. Раньше единственным способом проверить
настройки был реальный запуск в Telegram.

### 2.2. Что отдаёт `describe_module`

Ровно то, что перечислялось на созвоне:

1. **Все параметры** создания задачи — только те, что уходят в БД. Поисковые и
   чисто визуальные поля не включены, как и просили.
2. **Все ограничения каждого поля** — минимум, максимум, тип, обязательность, формат.
   Машинно, в JSON Schema, а не текстом в описании.
3. **Назначение каждого параметра** и **к какому блоку интерфейса он относится**.
4. **Расшифровка значений по смыслу**, а не по подписи. Не «postFilter: Только новые»,
   а «остаётся только самый свежий пост окна». Не «Консервативный», а «задержки ×1.8,
   вероятность не выше 25 %, минимальная длительность 60 минут».
5. **`whoAmI` по каждому модулю** (глобальный «about me» убран, как и просили): что
   делает, **чего НЕ делает**, что требуется, какие риски, как списываются деньги.
   Раздел «чего не делает» — не формальность: без него оркестратор выбирает не тот
   модуль, потому что «пишет текст» умеют трое.
6. **Примеры значений** у каждого поля и **готовые сценарии запуска** целиком.
7. **Ключевые слова для поиска.** Проверили спецификацию: штатного поля тегов в MCP
   нет — кладём в `_meta.tags` и дублируем слова в описании, чтобы поиск работал.

### 2.3. Слой «Помощь»

Каждый блок интерфейса доступен и инструментом `describe_block`, и ресурсом
`murmex://help/<модуль>/<блок>`: заголовок, что делает, как работает, **какой API
вызывает и какие поля этого API заполняет**. Это решает задачу «у меня список из
50 параметров, и я не знаю, к какому блоку они относятся».

### 2.4. Гарантия, что схема больше не соврёт

Это главное, а не объём описания.

Дескриптор модуля — не документация о коде, а **сам код**: из него собираются и
MCP-схема, и валидация. Поверх стоит **contract-тест**, который:

- сверяет список полей в схеме с полями, которые **реально читает воркер**;
  поле есть в коде, но нет в схеме → тесты красные, изменения не мержатся;
- ловит обратное: поле есть в схеме, но код его не читает — чтобы «мозги» не
  заполняли пустышки;
- сверяет **числа пресетов с поведением сервера**, а не с копией констант в тексте.

Дисциплина «не забудь обновить схему» уже один раз отказала — поэтому проверка машинная.
Напарнику отдано правило: новое поле регистрируется в дескрипторе тем же коммитом.

## 3. Покрытие

| Модуль | Статус | Параметров описано |
|---|---|---|
| Нейрокомментинг | ☑ | 30 |
| Нейрочаттинг | ☑ | 20 |
| Массовые реакции | ☑ | 17 |
| Остальные 12 | ☐ | по плану 18–22.08 |

Модули без схемы честно помечены `described: false` — «мозгам» видно, чему можно верить.
Раньше неописанный модуль выглядел так же полно, как описанный, и 5 полей принимались
за исчерпывающий список.

## 4. Что нашлось, пока сверяли схему с кодом

Всё это не было описано нигде и всплыло при разборе. Теперь в схеме:

- **`deadline`** читается всеми воркерами и останавливает уже идущую задачу — в схеме
  его не было вовсе;
- **`durationMinutes` — это МАКСИМУМ**, а не точная длительность: минимум задаёт
  уровень защиты (60 / 45 / 30 минут);
- **вероятность режется потолком защиты**: заданные 80 % при консервативном уровне
  фактически станут 25 %;
- **`protectionLevel` и `delayPreset` нумеруются в противоположном порядке** — у первого
  0 самый безопасный, у второго 0 самый быстрый;
- **пауза перед вступлением имеет жёсткий пол 60 с** и не ускоряется пресетом;
- **`aiMode` — мёртвое поле**: есть в типах, сервер его не читает (в схему не включено);
- у массовых реакций **вероятность проверяется дважды**, поэтому фактическая доля
  примерно равна квадрату заданной.

## 5. Как проверить

```bash
curl -X POST https://myrmexgram.ai/api/v1/mcp \
  -H "Authorization: Bearer <ключ>" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
       "params":{"name":"describe_module","arguments":{"module":"neuro-commenting"}}}'
```

Глазами, без JSON-RPC: `GET /api/v1/modules/neuro-commenting/describe`,
покрытие — `GET /api/v1/modules`.

## 6. Честно о границах

- **Живой прогон `create_task` через MCP на боевых аккаунтах не делался.** Инструмент
  готов и валидирует тем же кодом, что и `validate_task`, но реальную задачу через него
  пока не запускали — мешает инфраструктура: из 51 прокси в Telegram проходит 1,
  8 из 13 аккаунтов требуют переавторизации.
- Описано 3 модуля из 15. Остальные — по плану, дескрипторы делаются конвейером.
- SSE-поток не открывается: серверных уведомлений у нас нет, ответ приходит телом.
  Спецификация это допускает, клиентам достаточно.
