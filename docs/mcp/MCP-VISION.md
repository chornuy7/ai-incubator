# MCP — зачем, что сломано, куда идём

Источник: созвон **14.08.2026**, блок про MCP (01:00–01:12 записи). Формулировки заказчика
приведены дословно там, где это меняет требование.

---

## 1. Зачем это вообще нужно

Внешний AI-оркестратор («мозги») должен уметь **сам** составить задачу для модуля:
выбрать модуль, заполнить его параметры, не нарушить ограничения, объяснить человеку,
что он собрал и почему. Для этого ему нужно машиночитаемое, исчерпывающее описание
платформы — не документация для человека, а **контракт**.

> «Мне нужен MCP-сервер, который полностью опишет каждый параметр, который мы можем
> использовать и создавать внутри любого модуля».

Пока такого описания нет, «мозги» не пишутся. Это прямая блокировка:

> «Конкретно сейчас MCP-шка — это то, что держит меня дальше с производством мозгов,
> из-за этого я тоже встал».

## 2. Что сломано сейчас

**Проблема №1 — схема врёт.**

> «Ни хрена не соотносятся то, что написано в джейсоне, с тем, какие параметры реально
> есть у каждого модуля».

Так и есть. `GET /api/v1/mcp` собирается из `MODULE_DEFS` — а там на модуль всего
`idPrefix` / `requiresTargets` / `targetLabel`. Манифест обещает «мозгам» 5 полей
(`accountIds`, `targets`, `maxActions`, `goalId`, `campaignId`), тогда как реальный
нейрокомментинг принимает **более 25 параметров** (см. [MCP-MAP.md](./MCP-MAP.md)).
Оркестратор, написанный по этому манифесту, соберёт задачу, которая либо не запустится,
либо запустится не так, как задумано.

**Проблема №2 — это не MCP.**

`/api/v1/mcp` — обычный REST-эндпоинт, отдающий JSON со списком «tools». Настоящий MCP —
это протокол: JSON-RPC 2.0, `tools/list` → `tools/call`, транспорт Streamable HTTP,
`resources/*`, `prompts/*`. Никакой MCP-клиент к нашему эндпоинту не подключится.
Заказчик прав, что это «разные планеты».

> **Закрыто 14.08** (протокол) и **26.08** (текущая ревизия `2026-07-28`: рукопожатия
> больше нет, каждый запрос несёт версию сам, `server/discover` обязателен). Сервер
> обслуживает обе эры на одном адресе — детали в [MCP-SPEC.md §8](./MCP-SPEC.md).

**Проблема №3 — нет слоя смысла.**

Даже полный список полей бесполезен, если он плоский. В UI параметры сгруппированы в блоки
(«Выберите аккаунты», «Промпты», «Тайминги»), а в БД улетают одним списком:

> «У меня просто список 50 параметров списком, я из этих параметров не знаю, какому блоку
> и какой функциональной части они относятся».

## 3. Что требуется (полный разбор требований заказчика)

### 3.1. По каждому модулю

1. **Все параметры**, которые модуль использует для создания задачи. Только те, что
   **храним в БД** — UI-поля поиска/фильтрации не нужны («поисковые нам не надо, это бред»).
2. **Все ограничения каждого поля**: минимум, максимум, тип, обязательность, любые
   правила валидации («нельзя писать запятые в названии», «нельзя вставлять смайлики»).
   Пример заказчика: счётчик задержки не может быть меньше нуля — значит `minimum: 0`
   должен стоять в схеме, а не жить в голове разработчика.
3. **Назначение каждого параметра** — для чего он нужен и что конкретно делает.
4. **Принадлежность к блоку** — какой визуальный/функциональный блок его порождает.
5. **Расшифровка перечислений и пресетов.** Не «min/max/balance», а что каждое значение
   делает физически:
   > «MCP-шка должна написать: этот параметр account safety имеет 3 значения — min, max,
   > balance, где min обозначает, что аккаунт будет проверяться каждые 2 минуты, он может
   > писать 3 сообщения в неделю, это нужно для того, чтобы аккаунт не забанили».
6. **`who_am_i` на модуль, а не глобальный.** Глобальное «кто я» заказчик отверг прямо:
   «about me… оно нахер не нужно, это всё фуфло. Нам нужен who am I, но конкретно для
   каждого модуля» — чтобы при запуске MCP понимала, что делает **этот** модуль.
7. **MCP-оформление**: `title`, `description`, ключевые слова/теги, **примеры значений**
   для каждого параметра, **сценарии использования**.

### 3.2. Слой «Помощь» (support/обучение)

Отдельная подсистема, отвечающая на вопрос «что это за блок»:

- заголовок раздела (например, «Выберите аккаунт»);
- что этот блок делает и как работает;
- какие параметры в нём живут;
- **какой API он дёргает и какие поля этого API заполняет**.

Нужно, чтобы «мозги» на ходу обращались за пояснением и связывали плоский список
параметров с функциональными частями продукта.

### 3.3. Точность изложения

> «Заставь Клауд настолько подробно расписать каждый модуль, и каждый блок в модуле,
> и каждый параметр, насколько это вообще сухо возможно. Нужно очень-очень точно».

Отсюда правило раздела: **никаких примерных формулировок**. Каждое значение в карте
подтверждается кодом со ссылкой на файл. Если поведение неизвестно — пишем «не описано»,
а не догадку.

### 3.4. Визуализация

Заказчику визуализация не нужна («мне проще прочитать кодом»), но и не мешает.
Делаем по потребности, приоритет — нулевой.

## 4. Что реально умеет протокол MCP (проверка требований)

Заказчик просил проверить, а не поверить на слово. Проверено по спецификации протокола:

| Требование | Поддержка в MCP | Как делаем |
|---|---|---|
| `title` + `description` инструмента | **Да**, штатные поля | напрямую |
| Ограничения полей (min/max/pattern/enum) | **Да** — `inputSchema` это JSON Schema | `minimum`, `maximum`, `pattern`, `enum`, `required` |
| Примеры значений | **Да** — JSON Schema `examples` / `default` | на каждое поле |
| Сценарии использования | **Да** — в `description` инструмента и `_meta` | блок «Примеры» |
| **Поиск по тегам/ключевым словам** | **Нет штатного поля тегов.** Клиенты ищут по `name`/`description` | кладём `_meta.tags` **и дублируем ключевые слова в `description`**, чтобы поиск работал |
| Структурированный ответ | **Да** — `outputSchema` + `structuredContent` | описания модулей отдаём структурой, не текстом |
| Документы/справка | **Да** — `resources/*` | help по блокам как ресурсы `murmex://help/<module>/<block>` |

Единственное расхождение с ожиданием заказчика — теги: их в протоколе нет как отдельной
сущности. Решение выше (`_meta.tags` + ключевые слова в описании) закрывает задачу поиска
и ничего не ломает.

## 5. Целевая картина

```
                    ┌───────────────────────────────┐
   «Мозги» ──MCP──► │  MCP-сервер Murmex            │
   (оркестратор)    │  tools/list, tools/call       │
                    │  resources (help по блокам)   │
                    └──────────────┬────────────────┘
                                   │ читает
                    ┌──────────────▼────────────────┐
                    │  ДЕСКРИПТОРЫ МОДУЛЕЙ          │◄── единственный источник правды
                    │  server/mcp/descriptors/*.js  │
                    └──────────────┬────────────────┘
                        ┌──────────┼──────────┐
                        ▼          ▼          ▼
                   валидация    UI-схема   REST /api/v1
                   (registry)   (модули)   (capabilities)
```

Ключевое: дескриптор — **не документация о коде, а сам код**. Валидация запуска берёт
ограничения оттуда же, откуда MCP берёт `inputSchema`. Тогда «схема врёт» становится
невозможным состоянием, а не тем, что надо периодически чинить.

## 6. Границы (чего MCP не делает)

- Не отдаёт поисковые/UI-only поля — только то, что уходит в БД задачи.
- Не даёт доступа шире, чем есть у пользователя ключа: MCP работает от имени владельца ключа,
  RBAC применяется как для человека.
- Не подменяет собой «мозги»: MCP описывает и валидирует, решения принимает оркестратор.
- Не является платным ИИ-вызовом. Заказчик отдельно отметил: «если это запрос в ИИ — это жопа».
  Дескрипторы **статичны**, генерации на лету нет.

## 7. Почему это станет отдельным сервисом

Заказчик планирует Instagram отдельным сервисом с общими аккаунтами:

> «Это будет отдельный сервис… но при этом они будут шарить одни и те же аккаунты».

Значит описание возможностей должно жить **над** конкретной платформой: один MCP,
две (и более) реализации модулей. Отсюда и требование вести карту тщательно с самого
начала — она переживёт текущий монолит.
