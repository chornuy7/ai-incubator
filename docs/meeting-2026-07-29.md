## 1. Полные логи любого юзера в админке `[NEW — приоритет, юридический риск]`

Строки 1–25.

- Сейчас в админке видно только «юзер запустил нейрокомментинг + сколько списалось монет».
  **Этого мало.**
- Надо: по **любому** юзеру из админки смотреть **любые логи, любую активность, любые
  действия** — что именно он делает, **с кем переписывается**, и так далее.
- Мотив — не любопытство, а **ответственность**: *«это наша экосистема, внутри которой
  кто-то работает»*. Если юзер использует наших ботов не по назначению, отвечаем мы.
  *Цитата:* «если ты позволишь людям делать всякую хуйню внутри твоей системы используя
  твоих ботов — ты окажешься в местах не очень хорошего местожительства».
- Аналогия заказчика: любая крупная компания знает про каждый клик у себя в системе.
- **Только в админке** (не в кабинете юзера).

> ⚠️ **Зависимость:** пока данные не привязаны к юзеру (см. §3), «показать все действия
> юзера X» технически невозможно. Сначала БД — потом экран логов.

  *Цитата:* «чтобы мы не занимались этой хуйнёй и к этому потом не возвращались, потому

## 3. Supabase — переделать схему правильно `[NEW — крупный блок]`

Строки 59–235 (самый длинный кусок созвона).

Заказчик открыл нашу базу и разобрал ошибки по пунктам:

### 3.1. Данные не привязаны к юзеру `[критично]`
- Таблица `goals` = `id`, `name`, `created` — и всё. *«Цель должна быть завязана за
  юзером, который её создал. Она сейчас ни за что не завязана и просто висит в пустоте.»*
- Надо: **foreign key на user ID** во всех таблицах данных (кто создал, когда создал).
- Выгрузка данных в Supabase — *«классный первый шаг»*, но **шаг второй — связать их с
  юзером**.

### 3.2. auth.users vs profiles `[критично]`
- **Не создавать свою таблицу `users`** — она конфликтует со встроенной `auth.users`
  в Supabase, будут путаться.
- **`auth.users`** (встроенная в Supabase Auth) хранит только аутентификацию: e-mail,
  пароль, ID — 4–5 полей.
- **`profiles`** (наша таблица вместо `users`) хранит информацию о человеке. **E-mail в
  profiles не держим** — он живёт в auth-таблице.
- Заказчик просил почитать доку Supabase по auth.users.

### 3.3. Типизация — не текстом, а ссылкой `[критично]`
- *«Ты никогда не держишь типизацию в тексте — это поебень.»*
- Отдельная таблица типов (`user_types` / `user_privileges`): колонка `id` + `name`.
- **Имя типа уникальное** — нельзя создать два `administrator`. Плюс проверка **длины** и
  **паттерна** (только допустимые символы, без точек и постороннего) — **на уровне
  настроек таблицы в БД**, а не фильтром снаружи. Мотив: чтобы никто не заслал в таблицу
  произвольный код.
- В профиле пользователя хранится **`user_type_id`** — ссылка на строку в таблице типов.
- *«Ты всё делаешь ссылками. Когда редактируешь — редактируешь ссылку, а не текст.»*

### 3.4. Права: join-таблица `[критично]`
- Права доступа привязываются к типу: либо колонками внутри таблицы типов, либо (лучше)
  **третья таблица-связка**.
- Связка состоит из **двух референсов** в каждой строке: `user_type_id` + `module_id`.
  Пример: `T1→M1`, `T1→M2`, …
- Мотив: **чистое хранение данных** — таблица модулей остаётся «чистой как стёклышко»,
  только про модули; все связи живут в отдельных таблицах связей.
- Это правильный подход для Postgres/Supabase; выборка — через `join`/`where` по референсу.

### 3.5. Нет зарегистрированных юзеров в Supabase Auth
- В разделе Authentication пусто — *«косяк»*. Нужно **зарегистрировать себя и Илью**
  заново через Auth (сейчас доступ работает по старым данным).

## 4. Баланс: доллары отдельно, токены отдельно `[уточн. §10.1]`

Строки 241–257.

- Показывать «токены в долларах» — **не то**. *Цитата:* «не токены в долларах, мне нахрен
  эта бесполезная информация».
- Нужны **два независимых показателя**:
  1. **Баланс в долларах** (всегда в валюте): например, $100;
  2. **Количество токенов** у аккаунта: например, 13.
- Механика: докупил токенов → **доллары уменьшились, токены выросли** ($90 / 27 токенов).

## 5. Предупреждение о балансе — КРАСНОЕ `[уточн. §10.1]`

Строки 274–289.

## 6. Лендинг: у каждого модуля — картинка `[NEW, §10.6]`

Строки 294–332.

- **У каждого модуля должна быть картинка модуля.** *Цитата:* «никому не упало читать
  энциклопедию — все хотят смотреть глазками».
- Как делать: взять **скриншот модуля**, разбить **на куски/блоки** и к каждому дать
  подпись-сноску: «вот блок автоматизации», «вот блок комментинга», «вот это можно
  потыкать».
- Тон — продающий, а не справочный. Плохо: «здравствуйте, меня зовут Нейрокомментинг,
  я умею комментировать». Надо так, чтобы человек понял, **за что $192**.
- *Цитата:* «когда ты функцию продаёшь — должен объяснить, какого хера она такая дорогая».
- Место: страница модуля (кнопка «Подробнее»).

## 8. API-ключ «мозгов» — переделать в server-to-server `[уточн. §10.3]`

Строки 390–437.

- Илья сделал так, что **админ генерирует ключ конкретному пользователю** — **это не то**.
- *Цитата:* «эта апишка была, чтобы подключить мозги, а не для пользователя».
- Как надо: это **общение между серверами**. Наш сервер подключается к защищённому API
  «мозгов», предъявляя **TLS-сертификат либо ключ**. Ключ **прописан у нас**, а **не
  генерится в админке** и не выдаётся юзерам.
- *Цитата:* «либо у нас нет этого ключа доступа — и тогда мы идём на хуй».
- **Чтение всех логов через API — пока не нужно.**
- Илье задача: **самому протестировать** API (Python-скриптами), проверить не «что-то
  возвращается», а **что именно** и что ответ **осмысленно структурирован**.
- Правило от заказчика: *«когда ты сомневаешься — звони»*.
