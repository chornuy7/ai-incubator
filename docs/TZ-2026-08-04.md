# Техническое задание по правкам

Источник требований: расшифровка созвона от 04.08.2026.

## 1. Организация работы

- Перенести постановку и ведение задач в Jira.
- Каждую задачу оформлять отдельным конкретным техническим заданием.
- Использовать статусы: `Backlog`, `To Do`, `In Progress`, `AI Testing`, `Human Testing`, `Done`.
- Через AI разрешено создавать задачи и переводить выполненную разработку в `AI Testing`.
- Проверка и перевод задачи в `Done` выполняются вручную после проверки Ильёй.
- Задачи можно возвращать на предыдущие стадии.
- Не переводить одновременно большое количество задач в `In Progress`: в работе должно находиться ограниченное число выбранных задач.

## 2. Сайт и страницы модулей

### 2.1. Структура страницы модуля

- Перевести страницу в одноколоночную структуру на всю ширину.
- Блоки «Как это работает» и «Возможности модуля» разместить в одной строке в двух колонках.
- Остальные информационные блоки выводить на всю ширину страницы.
- Использовать одинаковый дизайн блока оплаты на всех страницах.
- На короткой странице размещать два блока оплаты: в начале и в конце.
- На более длинной странице допускается блок оплаты в начале, середине и конце.

### 2.2. Состояния блока оплаты

- Для незалогиненного пользователя или пользователя без подписки показывать оплату.
- Для залогиненного пользователя с активной подпиской вместо повторной стандартной оплаты показывать предложение апгрейда.
- Апгрейд должен предлагать переход на больший срок, расширенный пакет или пакет с большим количеством токенов.
- Годовая скидка должна управляться из админ-панели; на созвоне проверено значение 15%.

## 3. Подписки, токены и цены

### 3.1. Настройки подписки

- Добавить для каждой подписки отдельное поле количества подарочных токенов.
- Количество подарочных токенов задавать отдельно для каждого модуля и тарифа.
- При покупке нескольких модулей подарочные токены суммировать.
- Управление количеством подарочных токенов выполнять из админ-панели.
- Готовые наборы и периоды пока оставить без изменений.

### 3.2. Калькулятор тарифа

- Рядом с количеством подарочных токенов показывать их себестоимость в деньгах.
- Показывать количество действий, доступных за выданные токены для конкретного модуля.
- Расчёт выполнять отдельно для каждого модуля на основании стоимости одного действия.
- Подарочные токены из подписки не учитывать как отдельный доход: доходом является покупка плана.
- Покупку дополнительных токенов учитывать как отдельную денежную операцию.

### 3.3. Экономика

- Добавить расчёт доходов, расходов и маржи.
- Доходы формировать из покупок планов, токенов и пополнений.
- Расходы считать в деньгах на основании фактического использования действий и внутренней стоимости.
- Пересчитывать результат изменения цен в реальном времени на основании фактической статистики пользователей.
- Отображать экономику по серверам, включая расход ресурсов на количество аккаунтов.

### 3.4. Источник покупки

- В истории покупок показывать источник средств.
- Различать внешнее пополнение через платёжную систему и покупку с внутреннего кошелька.
- Добавить отдельную колонку `Source` либо визуально различать источники цветом.
- Не показывать остаток после каждой операции, если для определения источника он не нужен.

## 4. Пользователи и субпользователи

- Исправить расположение данных пользователя: вывести информацию одной колонкой и выровнять текст.
- Переименовать действие «Пополнить кошелёк» в «Пополнить токены» там, где начисляются именно токены.
- Сохранить возможность вручную начислять пользователю токены, включая тестовые начисления для фокус-группы.
- Для каждого пользователя хранить и показывать полную информацию и историю действий.
- Выдавать каждому пользователю уникальный ID.
- Добавить поиск по имени, email и ID.
- Добавить возможность блокировки пользователя.

### 4.1. Связь владельца и субпользователя

- В профиле субпользователя хранить `owner` со ссылкой на ID владельца.
- Синхронизировать зависимые статусы владельца и субпользователей через правила базы данных.
- Пользователь, оплативший подписку, является администратором своего рабочего пространства.
- Субпользователь может получать доступ только к тем модулям, которые оплачены владельцем.
- Роли и права субпользователей перенести из общей админ-панели в пользовательскую панель владельца.
- В общей админ-панели оставить управление доступами клиентов к оплаченным модулям, без назначения внутренних ролей клиента.

### 4.2. Баланс субпользователя

- По умолчанию использовать общий баланс владельца и субпользователей.
- При добавлении субпользователя дать выбор: общий баланс либо индивидуальный лимит токенов.
- Ограничение задавать непосредственно в момент добавления субпользователя.
- Рядом с лимитом показывать калькулятор доступного количества действий.

## 5. Админ-панель

### 5.1. Статистика и загрузка данных

- При переключении периодов отменять предыдущий API-запрос и запускать новый.
- Не показывать данные предыдущего периода под выбранным новым периодом.
- Пока данные загружаются, очищать область статистики и показывать явный статус загрузки выбранного периода.
- Кэшировать уже загруженные периоды и не запрашивать неизменившиеся данные повторно без необходимости.
- Для статистики использовать завершённые периоды либо срез данных на момент запроса.
- Проверить и оптимизировать связи и запросы Supabase, чтобы не загружать полные связанные таблицы без необходимости.

### 5.2. Мониторинг и отчёты

- Добавить автообновление мониторинга и задач с интервалом 10–30 секунд.
- Добавить автообновление во всех разделах, где данные должны обновляться без ручной перезагрузки.
- Объединить отчёт по модулям, статусам задач и ошибкам.
- Мониторинг оставить как технический раздел для состояния сервера и аккаунтов.
- В списке проблем показывать причину ошибки и данные логирования.
- Карточки аккаунтов сделать кликабельными и показывать полную информацию и действия, доступные в пользовательской панели.

### 5.3. Роли и доступы

- Заменить две галочки доступа одним понятным переключателем.
- В админ-панели показывать клиента и доступные ему модули/блоки.
- Возможность зайти под аккаунтом клиента и проверить его доступы сохранить.
- Внутренние роли команды клиента настраивать в пользовательской панели.

### 5.4. Аккаунты и группы

- Убрать из общей админ-панели управление распределением аккаунтов между сотрудниками клиента.
- Перенести ресурсы, группы аккаунтов и распределение аккаунтов в рабочую зону клиента.
- В пользовательской панели позволить владельцу назначать группы аккаунтов своим субпользователям.
- Разделить одиночные аккаунты и группы аккаунтов так, чтобы назначение каждого раздела было однозначным.

## 6. Парсер и база каналов

- Сохранять результаты парсинга в собственной базе данных.
- При повторном совпадающем запросе сначала возвращать данные из базы.
- Показывать дату последнего обновления данных.
- Выполнять регулярную ревизию сохранённых каналов; обсуждён режим обновления раз в неделю.
- Выделить сервисные аккаунты для ревизии и обновления устаревших данных.
- Запускать фоновый парсинг постоянно по актуальным тегам и темам.
- Распределять аккаунты между первичным сбором и повторной проверкой устаревших данных.
- Не показывать пользователю источник данных и название внешнего сервиса; использовать нейтральное название «Парсер».
- Вынести управление сессиями парсера в админ-панель.
- Поддержать массовое подключение сессий, отдельный отпечаток и прокси для каждой сессии.
- Для сессий, требующих повторной авторизации, предусмотреть повторное ручное подключение.
- Отдельно проработать автоматизацию авторизации и массового импорта сессий на следующем созвоне.

## 7. Логи, статистика и безопасность

- Хранить логи действий пользователей и субпользователей в базе данных.
- В пользовательской панели администратор должен видеть свои логи и логи своих менеджеров.
- В общей админ-панели показывать логи всех пользователей.
- В статистике группировать однотипные действия по модулям.
- Для каждого модуля показывать `Total`: количество действий и потраченных токенов.
- Для раздела обзора аккаунта разрешить просмотр только одного аккаунта одновременно.
- Не хранить переписки Telegram в этом разделе; подтягивать данные выбранного аккаунта.
- Доработать и протестировать отображение диалогов, групп и каналов.
- В разделе задач с ошибками выводить причину ошибки и связанные логи.

## 8. Поддержка и Help Center

- Интегрировать поддержку пользовательской панели с админ-панелью.
- Реализовать создание тикета, ответ администратора и историю переписки.
- Добавить в правом нижнем углу быстрый виджет поддержки с историей запросов.
- Переместить кнопку Help Center вниз.
- Не показывать кнопку открытия Help Center поверх уже открытого Help Center.
- Исправить навигацию и состояния выбранных категорий и статей.
- Убрать несвязанные материалы из раздела поддержки.

## 9. Обучение и документация

- Переработать обучение для каждого модуля в пошаговый формат.
- Для каждого модуля указать расположение в меню, назначение и перечень блоков.
- Для каждого блока дать отдельное краткое описание.
- Для каждой кнопки и настройки объяснить действие и результат нажатия.
- Использовать отдельные изображения блоков и элементов интерфейса, а не один общий скриншот модуля.
- Использовать изображения высокого качества.
- Добавить увеличение изображения по клику.
- Добавить изображения там, где сейчас шаги представлены только текстом.
- Сначала довести до рабочего состояния само обучение; фильтрацию обучения по оплаченной подписке выполнять после этого.

## 10. Пользовательская панель и навигация модулей

- Скрыть нерабочие разделы: «Аналитика», «Цели», «Агенты» и «Компании».
- Разделы скрывать без удаления кода.
- Скрыть кнопку «Создать компанию».
- Сгруппировать пункты бокового меню, чтобы сократить количество одновременно видимых функций.
- Не реализовывать адаптивную версию на текущем этапе.
- Проверить отображение интерфейса на ширине около 1400 px.
- Создать два окружения: development и production.

## 11. Интерфейс запуска модуля

- Скрыть или заблокировать кнопку запуска до заполнения обязательных полей.
- Явно сообщать пользователю, какие обязательные данные не заполнены.
- Разделить обязательные и необязательные настройки визуально и логически.
- Добавить внизу модуля пошаговый roadmap обязательных действий.
- Пример последовательности: выбрать аккаунт → выбрать канал/группу → запустить.
- Необязательные шаги не включать в основной roadmap либо показывать второстепенным серым состоянием.
- Нижнюю панель запуска сделать на всю ширину и прижать к нижнему краю без лишних отступов.
- Убрать кнопку «Готово», если она не выполняет действие.
- Устранить дублирование кнопок запуска.
- Настройки тайминга размещать до запуска.
- Переименовать непонятные поля в соответствии с фактическим действием.
- Поле обработки истории подписать как количество последних постов для обработки.

## 12. Папки, цели и чёрный список

- Исправить добавление и удаление элементов в папках.
- Сделать понятное управление папками и списком целей.
- Убрать необходимость отдельного действия «Сохранить в папку», если добавление уже выполнено.
- Исправить работу чёрного списка.
- Перед запуском корректно показывать выбранный аккаунт и количество целей.

## 13. Распределение процентов

- Не разрешать вводить значения, из-за которых общая сумма превышает 100%.
- Ограничивать максимальное значение непосредственно в поле, а не только показывать ошибку после ввода.
- Исправить ввод чисел с ведущим нулём.
- При первоначальном заполнении автоматически распределять 100% между параметрами поровну.
- Добавить возможность закрепить отдельное значение кнопкой-замком.
- При изменении незакреплённого значения автоматически и поровну перераспределять остаток между остальными незакреплёнными параметрами.

## 14. Аккаунты и прокси

- Сохранить массовый импорт аккаунтов и прокси.
- Поддерживать форматы sessions, JSON и data, включая поиск данных двухфакторной аутентификации в папках.
- Поддерживать прокси из базы, массовую вставку прокси построчно и ручное назначение прокси отдельным аккаунтам.
- Разрешить использование одного прокси несколькими аккаунтами.
- Добавить уведомление об успешном выполнении операций.
- Для проверок аккаунта показывать последний момент проверки.
- Исправить отдельные и совместные действия проверки спамблока и других статусов, чтобы интерфейс явно показывал, какие проверки были запущены.
- Добавить автообновление статусов задач и проверок.
- Модуль автоматизации пока оставить без изменений.

## 15. Подготовка к запуску

- Завершить проверку всех модулей и всех элементов управления.
- Протестировать каждую подписку через новый аккаунт: покупку, выдачу доступов и работу модуля.
- Подключить платёжную систему и протестировать оплату.
- Провести нагрузочное тестирование сервера.
- Перед production перейти на более мощный сервер.
- Привлечь фокус-группу и 3–4 пользователей с опытом работы с Telegram-сервисами для проверки удобства и функциональности.
- Скрыть неготовые функции до завершения их реализации.

## 16. Отдельные незавершённые вопросы

- Автоматизация авторизации большого количества сессий парсера требует отдельной проработки.
- CRM не завершена и требует отдельного тестирования.
- Telegram-сессии ещё не перенесены в базу из-за шифрования.
- Задачи активных воркеров остаются в памяти процесса и не могут быть перенесены в базу как живые процессы.
- Для завершения миграции необходимо вручную внести административные аккаунты.
- На следующей неделе необходимо обновить подписку Supabase.
