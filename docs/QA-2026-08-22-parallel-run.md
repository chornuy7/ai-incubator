# Прогон 22.08: все модули параллельно на живых аккаунтах

**Задача владельца:** запустить все модули одновременно на своих аккаунтах, смотреть,
как это работает — логи, задержки, многомодульность, сроки прогрева. Проверять **через
интерфейс руками**, не кодом. Результаты и скриншоты — в этот документ.

**Как работаем:** три роли. ПМ ведёт этот документ и решает, что важнее; тестировщик
щёлкает интерфейс и заполняет результаты; кодер чинит найденное. Найденное чинится
сразу, документ обновляется в том же проходе.

**Как работаем с браузером.** Прод открыт в обычном Chrome владельца (он там залогинен);
я работаю через расширение. Ограничение: скриншоты и выполнение скриптов возможны только
когда вкладка Murmex **активна** — если владелец переключится, доступным остаётся чтение
структуры страницы.

**Пароль.** Вход выполняет владелец сам: пароли не вводятся ни в форму, ни запросом.

### Упор, из-за которого прод-часть отложена

Работа с продом идёт через расширение в Chrome владельца. Пока он был за компьютером,
расширение отдавало и чтение, и выполнение скриптов. Как только он отошёл, активной в
Chrome стала страница самого расширения — и всё, кроме чтения структуры, начало отвечать
`Cannot access a chrome-extension:// URL of different extension`: ни клика, ни скриншота,
ни скрипта. Скриншоты не отдаются и во встроенном браузере (панель свёрнута).

Значит, разделы, где нужны реальные действия в Telegram, ждут владельца за компьютером.
Всё остальное — интерфейс, локи, расчёт задержек, тексты логов, поведение при стопе и
перезапуске — проверяется на локальном стенде и делается сейчас. Где проверено локально,
в таблицах помечено «(локально)»: это честно означает «механика верна, живой Telegram не
подтверждён».

**Важно про риск.** Прогон на живых аккаунтах — это настоящие действия в Telegram:
комментарии, личные сообщения, реакции, вступления в каналы. Возможны спамблоки и
FloodWait, и они не откатываются. Поэтому первый круг — на малых лимитах (1–2 действия
на аккаунт), и только потом объёмы.

### П0. Общее для всех модулей

**Где что лежит**

| Действие | Куда идти |
|---|---|
| Настроить и запустить модуль | `/panel/modules/<ключ>`; мейлинг — `/panel/mailing`, автопостинг — `/panel/autoposting` |
| Логи, прогресс, пауза, стоп | `/panel/tasks` («Дашборд задач») |
| Правка настроек уже созданной задачи | Карточка задачи в дашборде — работает, только когда задача **не** `running`/`queued` |
| Профиль усталости и распорядок | `/panel` (Менеджер аккаунтов) → выделить аккаунты → «Усталость и отдых» |
| Занятость аккаунта, пауза переключения | Карточка аккаунта — плашка «Перерыв между модулями» |
| Прокси | `/panel/proxies` |

**Круг действий в любом боевом модуле — один и тот же**

1. Блок «Выбор аккаунтов» — отметить 3 аккаунта (мейлинг и диалоги — 2).
2. Блок целей («Группы» / «Каналы» / «Получатели») — добавить 1–2 цели.
3. Блок «Защита и тайминги»: «Защита аккаунтов» = **Сбалансированный**, «Пресет темпа» =
   **Сбалансированный**, раскрыть «Расширенные настройки», поле
   «Сколько сделает 1 аккаунт для цели» — **от 1, до 1**. Пресет сам переключится на
   «Custom» — так и должно быть; задержки при этом остаются те же (множитель Custom = ×1).
4. Проверить строку «Общий лимит — авто»: должно быть `1 × число аккаунтов`.
5. Нажать «Начать». У боевых модулей (комментинг, чатинг, диалоги, реакции, мейлинг)
   выскочит подтверждение «Реальные действия в Telegram» — подтвердить.
6. Сразу перейти в «Дашборд задач» и открыть лог.

**Множители пауз** — чтобы сверять цифры из лога с настройками:
`пауза = случайное из [от, до] × уровень защиты × пресет темпа`

| Уровень защиты | Множитель | | Пресет темпа | Множитель |
|---|---|---|---|---|
| Консервативный | ×1.8 | | Агрессивный | ×0.6 |
| Сбалансированный | ×1 | | Сбалансированный | ×1 |
| Агрессивный | ×0.75 | | Консервативный | ×1.8 |
| | | | Custom | ×1 |

Источник — `server/lib/protection.js:4-12`. При рекомендованных настройках множитель = **1**,
то есть в логе должны быть ровно те секунды, что стоят в полях.

**Потолок вероятности.** При включённой «AI-защите» сервер режет вероятность:
Консервативный → не выше 25%, Сбалансированный → не выше 45%, Агрессивный → без потолка
(`server/lib/protection.js:44-51`). Ставить 100% при «Сбалансированном» бессмысленно — в
логе всё равно будет `Пропуск по вероятности (45%)`.

**Как быстро остановить**

- Одна задача: «Дашборд задач» → строка задачи → красный квадрат «Стоп».
- Все сразу: галочка «выбрать все» вверху списка → «Стоп (N)».
- Стоп «просит» воркера выйти; ожидания режутся кусками по секунде, поэтому нормальное
  время реакции — секунды. Висит в «Останавливается…» дольше минуты → пункт 8.1.
- Прогрев — только супер-админ (СФ-3).


### П2. Многомодульность: точный сценарий

Проверяем два разных правила — их легко перепутать:

- **Блокировка (lock)** — «один аккаунт = один модуль каждого типа». Два мейлинга на одном
  аккаунте нельзя, мейлинг + комментинг — можно. Прогрев не делится ни с кем
  (`server/lib/accountLocks.js:88-127`).
- **Занятость (busy)** — «один аккаунт = одно действие за раз». Пока аккаунт пишет коммент,
  реакции его не берут; при переходе из модуля в модуль выдерживается случайная пауза
  10–45 с (`server/lib/accountBusy.js`).

**Сценарий (с обходом СФ-1)**

| Шаг | Что делать | Что должно случиться |
|---|---|---|
| 1 | Выбрать 3 свободных активных аккаунта A1–A3, записать их имена | |
| 2 | Открыть **три вкладки**: Нейрокомментинг, Массовые Реакции, Масслукинг | |
| 3 | В **каждой** вкладке выбрать те же A1–A3 и настроить по карточкам П1. Ничего не запускать | Пикер пускает: аккаунты пока свободны |
| 4 | Запустить Нейрокомментинг | Задача «Выполняется» |
| 5 | Не трогая пикер, во второй вкладке нажать «Начать» на Массовых Реакциях | Кнопка активна, задача создаётся. Если сервер отказал — цитату ошибки в «Найденное» |
| 6 | То же для Масслукинга | Три задачи «Выполняется» на одних аккаунтах |
| 7 | Смотреть логи всех трёх задач в дашборде | См. таблицу строк ниже |
| 8 | Открыть карточку любого из A1–A3 в менеджере | Плашка «Перерыв между модулями» с текстом вида `Перерыв после «Нейрокомментинг»: 32 с, осталось 19 с` |
| 9 | Остановить одну задачу (например Масслукинг) | Две другие продолжают; в их логах аккаунт снова берётся |

**Строки, доказывающие, что многомодульность работает**

| Что проверяем | Дословная строка в логе |
|---|---|
| Запрет одновременных действий | `Пропуск: занят действием в модуле «Нейрокомментинг»` |
| Пауза при переключении | `Пропуск: пауза при переключении модулей Нейрокомментинг → Массовые реакции: назначено 32 с, осталось 19 с` |
| Ожидание освобождения | `Пауза 15 с — ждём аккаунт до 14:32:07 (занят действием в модуле «Масслукинг»)` |
| Карточка аккаунта | `Перерыв после «Нейрокомментинг»: 32 с, осталось 19 с` |

Названия модулей в этих строках — из `MODULE_LABELS` (`accountLocks.js:34-49`): Мейлинг,
Автопостинг, Нейрокомментинг, Нейрочаттинг, Массовые реакции, Масслукинг, Прогрев,
НейроДиалоги, GGR · Рейтинг, Парсинг…

**Прогрев как исключение (пункт 2.3).** Два направления, проверить оба:

1. Аккаунт работает в комментинге → открыть Прогрев и попытаться его выбрать.
   Ожидание: пикер не даст (СФ-1); если даст — форма скажет
   `N аккаунт(а) заняты работой — прогрев берёт только свободные профили`
   (`LiveModule.tsx:305-307`).
2. Аккаунт в прогреве (статус `warming`) → открыть Нейрокомментинг и попытаться его выбрать.
   Ожидание: аккаунт в разделе «Недоступны» с подписью `в прогреве`; попытка добавить — тост
   `Профиль недоступен · Аккаунт в прогреве — назначить в работу нельзя.`
   На сервере тот же запрет:
   `Прогрев не делит аккаунт с другими модулями: профиль греется, пока не готов к работе. <id> → <модуль>.`

**Карантин (пункт 2.4).** Аккаунт со статусом `quarantine` не берётся никуда: в пикере —
раздел «Недоступны», подпись `в карантине`; если он всё же попал в настройки задачи, в логе
будет `Пропуск: quarantine`, а на предстартовой проверке — `Аккаунт пропущен: в карантине`.

### П3. Задержки: какие цифры фиксировать

Смысл: не «выглядит правдоподобно», а **сверить число из лога с формулой**. Для каждой
строки — скопировать её из лога дословно и посчитать, попадает ли в норму.

**Числа-эталоны** (`server/lib/humanDelays.js:33-49`):

- скорость набора — **26–44 слова в минуту**, своя у каждого сообщения;
- «подумать перед первым словом» — 0.7–3 с;
- чтение входящего — 15 знаков в секунду, **но не меньше 3 с**;
- переключение между модулями — **10–45 с**.

**Таблица замеров** (заполняет тестировщик)

| № | Модуль | Строка из лога (скопировать дословно) | Что сверяем | Норма | Сходится? |
|---|---|---|---|---|---|
| З-1 | Нейрочаттинг | | скорость набора | `сл/мин` в диапазоне 26–44 | |
| З-2 | Нейрочаттинг | | скорость РАЗНАЯ у 3+ сообщений | значения не повторяются подряд | |
| З-3 | Нейрочаттинг | | пауза на чтение | `читает` ≥ 3 с | |
| З-4 | Нейрочаттинг | | набор пропорционален длине | `слов ÷ сл/мин × 60` ≈ показанные секунды (включая «на подумать») | |
| З-5 | Нейрокомментинг | | пауза перед комментарием | 30–120 с при множителе 1 | |

| Риск кластера | `Риск кластера (§4.4): <причина>` |

**Формула срока повторной попытки после промаха распорядка**
(`server/lib/accountFatigue.js:282-291`):

```
срок = 60 с × (1 − шанс) / шанс,  но не меньше 5 с и не дольше, чем до конца текущего часа
```

Проверочные точки: 89% ≈ 7 с, 50% = 60 с, 10% ≈ 9 мин.
Час берётся **киевский**, а не серверный (`SCHEDULE_TZ = 'Europe/Kyiv'`).

**Как заставить распорядок и усталость сработать за время прогона.**
Менеджер аккаунтов → выделить один **отдельный** аккаунт → «Усталость и отдых»:

| Поле | Значение для теста | Что проверяем |
|---|---|---|
| «1. Порог действия» | 1 | после первого же действия аккаунт уйдёт на отдых — пункт 3.8 |
| «2. Отдых после действия» | 0 ч 5 мин | увидим `отдыхает после нагрузки (ещё 5 мин)` и возврат через 5 минут |
| «3. Восстановление» | 0 ч 2 мин | счётчик тает на 1 каждые 2 минуты — пункт 3.9 |
| «Распорядок дня» → текущий час | **10%** | почти каждый ход будет `мимо`, срок повтора ≈ 9 мин — пункты 3.6 и 3.7 |
| «Сдвинуть у каждого аккаунта по-своему» | включить | проверка «свой распорядок у каждого» — пункт 1.6 |

Значения по умолчанию, с которыми аккаунты живут сейчас: порог **15**, отдых **45 мин**,
восстановление — одна единица за **12 мин** (`server/lib/accountFatigue.js:27-44`).
После теста вернуть обратно.

### П5. Прогрев: как проверить сроки за 20–30 минут

**Где в интерфейсе написан обещанный срок.** Страница `/panel/modules/warming`, секция
«Уровень прогрева» (`LiveModule.tsx:47,880-899`). Три варианта переключателя дословно:

```
Быстрый · 2 дня      Нормальный · 3–7 дней      Стандартный · 7–14 дней
```

Под переключателем подсказка: «Уровень задаёт темп (~40 / 20 / 10 действий в день) и
множитель пауз». Те же числа повторены в справке (`src/shared/config/helpDocs.ts:262-276`)
и в подсказках модуля (`src/shared/config/moduleDocs.ts:228`).

**Из чего срок складывается в коде.** Уровень задаёт ровно две вещи
(`server/lib/workerLoop.js:8-18`):

| Уровень | Множитель пауз | «Действий в день» | Фактическая пауза между действиями |
|---|---|---|---|
| Быстрый (2 дня) | ×0.8 | 40 | **24–72 с** |
| Нормальный (3–7 дней) | ×1.3 | 20 | **39–117 с** |
| Стандартный (7–14 дней) | ×2.0 | 10 | **60–180 с** |

База — `pickDelay(30, 90, mul)`, `workers.js:1460`.
**«Действий в день» нигде не применяется**: единственное использование — строка лога старта
(`workers.js:1344`). Дневного дросселя, ожидания до следующего дня и ночной паузы нет.

**Что мерить за 20–30 минут наблюдения**

| № | Замер | Как |
|---|---|---|
| П5-1 | Обещание | Скриншот секции «Уровень прогрева» с выбранным уровнем |
| П5-2 | Строка старта | Скопировать `Прогрев запущен · уровень: … · ~N действий/день на аккаунт` |
| П5-3 | Действий за 20 минут | Посчитать строки `Прогрев: …` в логе ровно за 20 минут |
| П5-4 | Средняя пауза | Взять 5 подряд идущих строк, посчитать разницу по времени, усреднить |
| П5-5 | Темп в пересчёте на сутки | `П5-3 × 3 × 24`, поделить на число аккаунтов |
| П5-6 | Сравнение | Сравнить П5-5 с обещанными 40 / 20 / 10 |
| П5-7 | ETA в дашборде | Открыть карточку задачи прогрева, записать показанную оценку («≈ N дн») |
| П5-8 | Реальный финиш | Дождаться `Прогрев завершён` или зафиксировать прогресс на момент остановки |

**Ориентир для П5-6.** Средняя пауза на «Стандартном» ≈ 120 с — значит при непрерывной
работе одного аккаунта выходит ≈ 720 действий в сутки против обещанных 10. ETA в дашборде
рисуется отдельной формулой на фронте (`TasksPage.tsx:68-98`:
`остаток действий ÷ действий-в-день × сутки`) и с реальным поведением воркера не связан.
Задача заканчивается по количеству действий (цель 1…100), а не по времени: при цели 60 и
одном аккаунте это ≈ 78 минут на «Нормальном», а не 3–7 дней.

**Что ещё зафиксировать по разделу 5**

- 5.4: аккаунт в прогреве не берётся другими модулями — проверяется по П2, второе направление.
- 5.5: прерывание прогрева — под не-супер-админом кнопка «Стоп» в строке задачи активна, но
  сервер отвечает 403 с текстом
  `Останавливать и ставить на паузу прогрев может только супер-админ: это недели работы аккаунтов, откатить нельзя.`
  Массовый стоп фронт ловит заранее тостом `Прогрев остановить нельзя`. Записать оба поведения.
- Даты окончания прогрева и «дня прогрева» в интерфейсе нет. Плашка `Активен (Nд)` в
  карточке аккаунта — это **возраст аккаунта**, а не день прогрева
  (`server/accountStats.js:470`).
