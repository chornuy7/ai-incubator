## Порядок работ (оценка приоритета)

**Критический путь — БД первая.** Пункт «логи любого юзера в админке» невозможно закрыть,
пока данные не привязаны к юзеру: показать «все действия юзера X» не из чего. Поэтому
БЛОК A (схема) идёт **до** БЛОКА B (экран логов).

| # | Блок | Почему такой приоритет |
|---|------|------------------------|
| 1 | **A. Схема БД** | блокер для логов; чем дольше живут данные без владельца, тем дороже миграция |

## БЛОК A. Supabase — правильная схема `[§11.3, критично]`

- ◐ **Привязать данные к юзеру:** миграция `2026-07-30-owner-and-types.sql` добавляет
  `user_id` + FK (`on delete set null`) и индексы в `goals`, `campaigns`, `leads`,
  `parsed_channels`, `accounts_meta`. Код уже пишет владельца при создании цели и
  кампании (лиды — при записи), личность берётся из **подписанной сессии**
  (`sessionGuard` срезает присланный клиентом заголовок — клиент не источник личности).
  Помощник `lib/ownerColumn.js`: дублирует владельца в `data`, а при вставке откатывается
  на вариант без колонки, если миграция ещё не применена — сборка работает и до, и после.
  **Миграция применена 30.07** (боевая база). Проверено вживую: цель, созданная с подписанной
  сессией, пишет и читает `userId` из колонки, предупреждений о деградации нет. Записи,
  созданные раньше, остаются без владельца — приписывать их задним числом нечему.
- ☐ **Разделить auth и profile:** не держать свою таблицу `users` (конфликт со встроенной
  `auth.users`). Создать **`profiles`**; e-mail/пароль остаются в `auth.users`.
- ◐ **Типы юзеров — отдельной таблицей** (`user_types`): в миграции — `name` **UNIQUE**
  + CHECK на длину (2–40) и на паттерн (`^[a-z][a-z0-9_-]*$`), сид из трёх типов,
  ссылка `users.user_type_id`. **Наполнено из реальных ролей 30.07** (`lib/typesSync.js`):
  `user_types.name` = id роли (латинский, проходит CHECK), `title` = её имя;
  `users.user_type_id` = первая роль юзера. Типы-сироты из сида миграции удалены.
- ◐ **Права — join-таблицей:** `modules` (15) + `user_type_modules` (44 связи) наполнены из
  прав ролей и **пересобираются автоматически** при создании/правке/удалении роли.
  Проверено: добавили модуль роли — связей стало 3, убрали — снова 2.
  **Осталось (осознанно не сделано):** переключить сам гейт `can()` на эти таблицы.
  Причина: наша модель прав богаче схемы «тип↔модуль» — есть ещё блоки внутри модуля,
  разделы панели и ресурсы. Пока это ПРОЕКЦИЯ модульного среза в нормальные таблицы,
  а источник правды — `roles.permissions`. Переключать гейт на боевой базе можно только
  с тестами на новый путь, иначе ошибка молча снимет людям доступ.
- ☐ **Зарегистрировать реальных юзеров в Supabase Auth** (себя + Илью); сейчас раздел
  Authentication пуст, доступ живёт на старых данных.

## БЛОК B. Логи и активность юзера в админке `[§11.1, приоритет]`

- ☑ В карточке юзера (админка) — **журнал активности**: входы/выходы, запуски и остановки
  задач, изменения баланса/подписки/ролей/цен, API-ключи, статусы аккаунтов. Источник —
  аудит; эндпоинт `GET /api/admin/user-activity?userId=` (`userActivity()` в adminStats).
  Показываются и действия юзера, и действия **над ним** (пометка «над ним»).
  Проверено вживую: 123 события по админу, читаемые причины («Баланс usr_admin: 3 → 79.4»).
- ☑ **Фильтр по типу события** — чипы из фактически встреченных типов; событие с IP
  показывает IP прямо в строке.
- ☑ Только в админке (гейт `isAdminRequest`, иначе 403).
- ◐ **С кем переписывается** — блок в карточке юзера: с кем, каким аккаунтом, в каком
  статусе, когда. Связь строим двумя путями: по владельцу лида (`userId`, §11.3) и по
  аккаунтам из его задач (так видно и старые записи без владельца — помечены «по аккаунту»).
  `GET /api/admin/user-dialogs?userId=`. Проверено на изолированных данных: свои находятся,
  чужие не подмешиваются. **Тексты сообщений не отдаём** — их хранение остаётся открытым
  вопросом (приватность и объём), а «кто/каким аккаунтом/в каком статусе» отвечает на
  вопрос заказчика, не заводя нового хранилища.
- ☑ **Пробел атрибуции закрыт:** транспорт чинит `installFetchAuth` (Илья) — `X-User-Id`
  уходит со всеми запросами к /api; плюс убраны три хардкода `initiator='operator'`
  (расписание кампании, импорт аккаунтов, запуск кампании). 259 старых обезличенных
  записей остаются историей — их привязать не к чему.
- ☑ **[РЕШЕНО 30.07]** Тексты сообщений храним **целиком** — «нам нужно всё, чтобы был
  доступ ко всему». Реализовано: таблица `messages` (миграция `2026-07-30-messages.sql`),
  запись из нейродиалогов, нейрочаттинга и ЛС-рассылки (обе стороны переписки),
  `GET /api/admin/messages` (только админ), раскрытие переписки по клику на собеседнике
  в карточке юзера. Запись best-effort — логирование не роняет сам диалог; текст режется
  по 4000 символов с явной пометкой об обрезке.
  ⚠️ Это персональные данные третьих лиц: доступ только у админа, ретеншн не задан
  (по решению владельца «храним всё») — когда объём станет заметен, добавить чистку.

## БЛОК C. Блокировка юзера и IP `[§11.9]`

- ☑ **Заблокировать юзера** — уже работает кнопкой «Отключить» в карточке: `active=false`
  закрывает и вход (`authenticate` возвращает null), и текущую сессию (`/me` → 401
  «Пользователь отключён»). То есть это полная блокировка, а не только снятие модулей.
- ☑ **Логировать IP входа** — пишется в аудит при входе и при неудачной попытке
  (`x-forwarded-for` → сокет). В карточке юзера — блок **«Последний вход»**: дата + IP
  (у записей до этой правки — «IP не записан»). Проверено: попытка входа записала `ip: 127.0.0.1`.

## БЛОК D. Баланс и предупреждения `[§11.4, §11.5]`

- ◐ **Разделить баланс:** в шапке теперь ДВА числа — **$ (по курсу пакетов)** и **⚡ монеты**,
  разделены чертой; «токены в долларах» одним числом убрано. Проверено: 15 ⚡ → $1.20 (курс
  берётся из пакетов, та же формула, что в `coinUsdRate` на сервере).
  **Осталось (решение по биллингу):** сейчас монеты — это и есть кошелёк, а доллар считается
  из них. В модели заказчика доллар и токены — два независимых остатка (докупил токены →
  доллары ↓, токены ↑). Это переделка биллинга, а не отображения — выносится отдельно.
- ☑ **Красное предупреждение:** чип баланса в шапке на нуле/почти нуле — красный и со словом
  **«Пополнить»** (пороги общие с лентой: `CRITICAL` из LowBalanceBar); кнопки «Пополнить»
  в модалках (нет монет / низкий баланс на входе) — красные вместо зелёного `btn-primary`.
  Проверено вживую: при балансе 0.00 чип красный, текст «0.00 Пополнить».

## БЛОК E. Цены, подписки, периоды `[§11.2]`

- ☑ **Периоды — генерируемый список:** в админке (вкладка «Цены» → «Периоды подписки и
  скидки») список с кнопкой «+ Добавить период»; единица и количество — **селектами**
  (недели 1–4, месяцы 1–6, годы 1–5), скидка в % рядом, удаление корзиной. Хранится в
  `price_overrides.periods`, нормализуется на сервере (единица из белого списка, пределы, дубли,
  скидка 0–90%, сортировка по длительности).
- ☑ **Скидка за 6 месяцев** — добавляется этим же списком, без правки кода; переключатель
  на витрине и в калькуляторе строится из периодов (`/api/subscription` отдаёт `periods`).
  Пока админ ничего не задал — прежнее поведение (месяц + год со скидкой annualDiscount).
- ☑ **Миграция применена 30.07** (`2026-07-30-price-periods.sql`, боевая база). Проверено:
  период «6 месяцев −10%» сохраняется, доходит до витрины и считается верно
  ($120.25/мес → $649 за 6 мес). Деградации в логе больше нет.
  ⚠️ Значение скидки 6 мес (10%) выбрано для проверки — поменяйте в админке под себя.
- ☑ **Цена подписки за модуль** редактируется **и в админке, и в кабинете** («и там и там»):
  в кабинете (`/panel/user/subscription`) админ правит цену прямо в строке модуля
  (Enter или уход с поля), обычный юзер видит цену текстом. Пишется в тот же прайс, что
  и админка, поэтому витрина и счёт меняются вместе. Проверено вживую: 25 → 26 сохранилось
  на сервере, возвращено обратно.
- ☑ Цены модулей и годовая скидка правятся из админки и подтягиваются на лендинг
  (сделано ранее; на созвоне принято).
