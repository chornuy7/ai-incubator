## БЛОК A. Supabase — правильная схема `[§11.3, критично]`

- ☑ **Привязать данные к юзеру:** миграция `2026-07-30-owner-and-types.sql` добавляет
  `user_id` + FK (`on delete set null`) и индексы в `goals`, `campaigns`, `leads`,
  `parsed_channels`, `accounts_meta`. Код уже пишет владельца при создании цели и
  кампании (лиды — при записи), личность берётся из **подписанной сессии**
  (`sessionGuard` срезает присланный клиентом заголовок — клиент не источник личности).
  Помощник `lib/ownerColumn.js`: дублирует владельца в `data`, а при вставке откатывается
  на вариант без колонки, если миграция ещё не применена — сборка работает и до, и после.
  **Миграция применена 30.07** (боевая база). Проверено вживую: цель, созданная с подписанной
  сессией, пишет и читает `userId` из колонки, предупреждений о деградации нет. Записи,
  созданные раньше, остаются без владельца — приписывать их задним числом нечему.
- ◐ **Разделить auth и profile** — подготовлено, вход уже переключён двухрежимно:
  [RUNBOOK-auth-profiles.md](./RUNBOOK-auth-profiles.md) (порядок работ, SQL, план отката).
  Почему не выкатили целиком: на `users.id` завязаны FK **13 таблиц**, а пароли в
  `auth.users` не переносятся из нашего `password_hash` — людям придётся задать пароль
  заново.
  **30.07 — вход двухрежимный:** `/login` сначала проверяет пару через **Supabase Auth**
  (`verifyAuthPassword` на одноразовом клиенте), при промахе падает на legacy scrypt-хэш.

  без «окна, когда вход не работает». Auth-аккаунт маппится на нашу учётку по

  В аудит входа пишем, каким путём вошли (`via: supabase|legacy`). Осталось: завести людей
  в Auth и задать пароли (действие человека), затем — при желании — выключить legacy-ветку.

## БЛОК B. Логи и активность юзера в админке `[§11.1, приоритет]`

- ☑ В карточке юзера (админка) — **журнал активности**: входы/выходы, запуски и остановки
  задач, изменения баланса/подписки/ролей/цен, API-ключи, статусы аккаунтов. Источник —
  аудит; эндпоинт `GET /api/admin/user-activity?userId=` (`userActivity()` в adminStats).
  Показываются и действия юзера, и действия **над ним** (пометка «над ним»).
  Проверено вживую: 123 события по админу, читаемые причины («Баланс usr_admin: 3 → 79.4»).
- ☑ **Фильтр по типу события** — чипы из фактически встреченных типов; событие с IP
  показывает IP прямо в строке.
- ☑ Только в админке (гейт `isAdminRequest`, иначе 403).
- ☑ **Журнал сделан заметным (31.07):** «все действия юзера» поднято ВВЕРХ карточки (сразу под
  «Последний вход»), с акцентным заголовком и иконкой — раньше был в самом низу и его не находили.
  Подсказка над таблицей переписана: «нажмите на строку — все действия юзера».
- ☑ **С кем переписывается** — блок в карточке юзера: с кем, каким аккаунтом, в каком
  статусе, когда. Связь строим двумя путями: по владельцу лида (`userId`, §11.3) и по
  аккаунтам из его задач (так видно и старые записи без владельца — помечены «по аккаунту»).
  `GET /api/admin/user-dialogs?userId=`. Проверено на изолированных данных: свои находятся,
  чужие не подмешиваются. **Тексты сообщений не отдаём** — их хранение остаётся открытым
  вопросом (приватность и объём), а «кто/каким аккаунтом/в каком статусе» отвечает на
  вопрос заказчика, не заводя нового хранилища.
- ☑ **Пробел атрибуции закрыт:** транспорт чинит `installFetchAuth` (Илья) — `X-User-Id`
  уходит со всеми запросами к /api; плюс убраны три хардкода `initiator='operator'`
  (расписание кампании, импорт аккаунтов, запуск кампании). 259 старых обезличенных
  записей остаются историей — их привязать не к чему.
- ☑ **[РЕШЕНО 30.07]** Тексты сообщений храним **целиком** — «нам нужно всё, чтобы был
  доступ ко всему». Реализовано: таблица `messages` (миграция `2026-07-30-messages.sql`),
  запись из нейродиалогов, нейрочаттинга и ЛС-рассылки (обе стороны переписки),
  `GET /api/admin/messages` (только админ), раскрытие переписки по клику на собеседнике
  в карточке юзера. Запись best-effort — логирование не роняет сам диалог.
  **[РЕШЕНО 03.08] Глубина хранения — БЕЗ обрезки, храним весь текст** («у нас должно быть
  всё»): дефолтный лимит 4000 символов снят, обрезка теперь только по явному env
  `MESSAGES_MAX_TEXT` (аварийный рычаг, по умолчанию 0 = без лимита). Тесты — `messages.test.js`.
  ⚠️ Это персональные данные третьих лиц: доступ только у админа, ретеншн не задан
  (по решению владельца «храним всё») — когда объём станет заметен, добавить чистку.
- ☑ **Нагрузка сервера в мониторинге (30.07):** живой блок «Нагрузка сервера» — **RPS**
  (запросов/сек, среднее за минуту) и загрузка **CPU/памяти** процесса, опрос раз в 3 с.
  Метрика считается в самом процессе без внешних агентов: RPS — кольцо посекундных корзин
  (память не растёт под нагрузкой), CPU% — дельта `process.cpuUsage()`, RSS показывается
  против лимита ≤3 ГБ. `GET /api/admin/system` (только админ), `server/lib/systemMetrics.js`.
- ☑ **Корзина аккаунтов прямо в админке (30.07):** во вкладке «Аккаунты» переключатель
  «Рабочие / Корзина», мягкое удаление, восстановление и очистка корзины — чтобы не ходить
  за этим в Менеджер профилей. Тяжёлый мастер импорта не дублируем: кнопка «Импорт» ведёт
  в Менеджер профилей.

## БЛОК D. Баланс и предупреждения `[§11.4, §11.5]`

- ☑ **Разделить баланс** — сделано по модели владельца (30.07): «$ — основное, за них
  покупаем подписки и токены; токены тратятся на действия в модулях».
  - `coin_balance.usd` (миграция `2026-07-30-usd-wallet.sql`) — денежный остаток, отдельно
    от токенов (`coins` оставлено как есть: это и есть счётчик токенов, переименование
    поля означало бы переписывать биллинг и рисковать деньгами клиентов);
  - `changeUsd()` — движение денег, `buyTokens({usd})` — покупка токенов по курсу пакетов
    («$ ↓, токены ↑»). Деньги списываются ПЕРВЫМИ, при сбое начисления возвращаются;
  - `POST /api/balance` принимает `usd` (пополнение деньгами) наравне с `amount` (токены);
  - `POST /api/balance/buy-tokens` — себе сам, другому только админ;
  - в шапке $ теперь настоящий остаток с сервера, а не пересчёт токенов по курсу.
  Покрыто тестами (покупка, нехватка средств, изоляция кошельков) — 551/551.
- ☑ **$ — приоритет в интерфейсе (31.07):** «кошелёк» показывает $ ПЕРВЫМ, токены — вторично.
  - модалка кошелька в шапке: плитка **«Деньги $»** (основное) + **«Токены ⚡»** + блок
    **«Мои модули»** (что открыто) — всё в одном месте; секции «Пополнить $» и «Купить токены за $»;
  - админка «Пользователи», колонка «На счету»: `$X.XX` крупно + `⚡` мельче; кнопка «+»
    пополняет **доллары** (суффикс ⚡ — токены). `usdByUser()` + `usd` в usersReport и итогах;
  - облик учёта («депозит $ = выручка») отложен до подключения платёжки: реальных депозитов $
    пока нет, деньги заводит только админ.
- ☑ **Красное предупреждение:** чип баланса в шапке на нуле/почти нуле — красный и со словом
  **«Пополнить»** (пороги общие с лентой: `CRITICAL` из LowBalanceBar); кнопки «Пополнить»
  в модалках (нет монет / низкий баланс на входе) — красные вместо зелёного `btn-primary`.
  Проверено вживую: при балансе 0.00 чип красный, текст «0.00 Пополнить».
