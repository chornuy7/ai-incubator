## Порядок работ (оценка приоритета)

**Критический путь — БД первая.** Пункт «логи любого юзера в админке» невозможно закрыть,
пока данные не привязаны к юзеру: показать «все действия юзера X» не из чего. Поэтому
БЛОК A (схема) идёт **до** БЛОКА B (экран логов).

| # | Блок | Почему такой приоритет |
|---|------|------------------------|
| 1 | **A. Схема БД** | блокер для логов; чем дольше живут данные без владельца, тем дороже миграция |
| 2 | **B. Логи юзера в админке** | юридический риск — заказчик обозначил как ответственность, а не фичу |
| 3 | **C. Блокировка юзера + IP** | тот же контур безопасности, дёшево делается вместе с B |
| 4 | **D. Баланс $ / токены + красное** | деньги видит каждый юзер; правка небольшая |

## БЛОК A. Supabase — правильная схема `[§11.3, критично]`

- ☐ **Привязать данные к юзеру:** `foreign key` на user ID во всех таблицах данных
  (`goals`, `campaigns`, `leads`, `tasks`, `accounts_meta`, результаты парсеров …).
  Поля «кто создал» + «когда создал». Сейчас записи «висят в пустоте».
- ☐ **Разделить auth и profile:** не держать свою таблицу `users` (конфликт со встроенной
  `auth.users`). Создать **`profiles`**; e-mail/пароль остаются в `auth.users`.
- ☐ **Типы юзеров — отдельной таблицей** (`user_types`): `id` + `name`, где `name`
  **UNIQUE** + проверка длины + проверка паттерна (CHECK-констрейнты на уровне БД,
  не фильтром в коде). В `profiles` — `user_type_id` (ссылка).
- ☐ **Права — join-таблицей:** `user_type_id` ↔ `module_id` (две ссылки в строке).
  Таблица модулей остаётся чистой, все связи — во внешних таблицах связей.
- ☐ **Зарегистрировать реальных юзеров в Supabase Auth** (себя + Илью); сейчас раздел
  Authentication пуст, доступ живёт на старых данных.
- ☐ Миграция существующих данных под новую схему (без потери того, что уже выгружено).

## БЛОК B. Логи и активность юзера в админке `[§11.1, приоритет]`

- ☐ В карточке юзера (админка) — **полный журнал**: любые действия, любая активность,
  запуски, изменения, авторизации.
- ☐ **С кем переписывается** — переписки/диалоги, которые ведут его аккаунты.
- ☐ Фильтры: по дате, по модулю, по аккаунту, по типу события; поиск.
- ☐ Только в админке (в кабинете юзера этого нет).
- ☐ **[❓]** Согласовать глубину: хранить ли тексты сообщений целиком (объём + приватность).

## БЛОК C. Блокировка юзера и IP `[§11.9]`

- ☐ **Заблокировать юзера** — отдельно от «выключить» (которое снимает модули).
  Заблокированный не может делать ничего; статус снимается вручную после разбирательства.
- ☐ **Логировать IP входа** — видеть, откуда заходят (сценарий: доступ забрал уволенный
  сотрудник).

## БЛОК D. Баланс и предупреждения `[§11.4, §11.5]`

- ☐ **Разделить баланс:** отдельно **$ (валюта)**, отдельно **количество токенов**.
  Покупка токенов: доллары ↓, токены ↑. Не показывать «токены в долларах».
- ☑ **Красное предупреждение:** чип баланса в шапке на нуле/почти нуле — красный и со словом
  **«Пополнить»** (пороги общие с лентой: `CRITICAL` из LowBalanceBar); кнопки «Пополнить»
  в модалках (нет монет / низкий баланс на входе) — красные вместо зелёного `btn-primary`.
  Проверено вживую: при балансе 0.00 чип красный, текст «0.00 Пополнить».

## БЛОК E. Цены, подписки, периоды `[§11.2]`

- ☐ **Периоды — генерируемый список:** кнопка «+» добавляет период, период выбирается
  **селектом**: недели 1–4, месяцы 1–6, годы 1–5. Убирает будущие переделки.
- ☐ **Скидка за 6 месяцев** (меньше годовой) — как второй вариант рядом с годовой.
- ☐ **Цена подписки за модуль** редактируется **и в админке, и в кабинете** («и там и там»).
- ☑ Цены модулей и годовая скидка правятся из админки и подтягиваются на лендинг
  (сделано ранее; на созвоне принято).

## БЛОК F. Лендинг `[§11.6, §11.7]`

- ☐ **Картинка у каждого модуля**: скриншот модуля, разбитый на блоки с подписями-сносками
  («вот блок автоматизации», «вот блок комментинга»). Продающий тон — объяснить, за что
  цена. Место: страница модуля («Подробнее»).
- ☑ **Шапка для залогиненного:** аватар + имя + кнопка **«Кабинет»** (ведёт в /panel) вместо
  «Войти»; гостю по-прежнему «Войти». Общий компонент `landing/AuthCta.tsx` — одинаково на
  лендинге и на странице модуля. Проверено вживую в обоих состояниях.
- ☑ Клик по логотипу ведёт на лендинг — принято на созвоне.
- ⏸ Шаблоны и блок скидок-наборов — **пока не трогаем** (по решению заказчика).

## БЛОК G. API «мозгов» — server-to-server `[§11.8, Илья]`
