## A. ИЕРАРХИЯ Цель→Кампания→Задача→Агент (Фаза A3)

### A3.1 Убрать из Цели то, что принадлежит Агенту
**Почему:** заказчик прямо сказал — тон/ограничения/дожим в цели это ошибка (SPEC §1.2).
Сейчас поля `toneOfVoice`, `restrictions`, `followUp` живут и в Goal (deprecated), и в Agent.
- Файлы: `server/goals.js` (убрать поля из FIELDS/normalizeGoal), `src/api/goalsApi.ts`,
  `src/pages/GoalsPage.tsx` (убрать блоки тон/ограничения/дожим из формы),
  `server/lib/goalContext.js` (перестать класть тон/ограничения в промпт — это делает
  `buildAgentContext`).
- Оставить у цели: измеримый результат (leadTarget), критерий завершения, дедлайн, аудиторию.
- **Свободный текст цели** (SPEC §1.1): описание принимает любой текст желания.
- Приёмка: цель без тона/дожима; старые цели читаются (миграция не нужна); тесты зелёные.

### A3.2 Выбор Агента в задаче кампании
**Почему:** агент выбирается на уровне задачи (пример «500 хвалят / 500 спорят», SPEC §2.6).
- В форме кампании у каждой строки-модуля — дропдаун «Агент» (список из `/api/agents`).
- Хранить `agentId` на строке модуля кампании (`modules[]` → `[{moduleKey, agentId}]` или
  параллельный массив). Прокинуть `agentId` в задачу при запуске (`launchCampaign`).
- Файлы: `src/pages/CampaignPage.tsx`, `server/campaigns.js`, `server/campaignsRoutes.js`,
  `src/api/campaignsApi.ts`.
- Приёмка: выбрал агента в строке → задача стартует с его тоном.

### A3.3 Провод Агента в воркеры (промпт)
**Почему:** модули должны брать тон из выбранного агента, а не из цели.
- В `server/modules/workers.js`: где сейчас `+ goalCtx`, добавить `+ agentCtx`
  (`buildAgentContext(settings.agentId)`). Затрагивает комментинг/чатинг/диалоги/мейлинг.
- Приёмка: живой прогон — тон в сообщении соответствует агенту; дожим берётся из агента.

## D. ПОВЕДЕНИЕ АККАУНТОВ — усталость, лимиты, распорядок (SPEC §4)

> Заказчик особо просил: **у каждого аккаунта — усталость, лимиты, настройки; и чтобы
> можно было МАССОВО всем задавать усталость и отдых от модулей, чтобы выглядели как
> живые люди.** Это второй, более сложный этап; заложить модель уже сейчас.

### D1. Статистика и усталость ВНУТРИ аккаунта (кросс-модульно)
- Хранить у аккаунта (`accounts-meta` или отдельный `server/accountActivity.js`):
  накопленные действия за период, время последнего действия, «усталость».
- Усталость растёт от действий (любого модуля), падает во время отдыха. Устал → аккаунт
  недоступен, пока не отдохнёт. Отдых — не только внутри модуля, а между модулями/днём.
- Приёмка: аккаунт после N действий уходит «на отдых» во ВСЕХ модулях, не только в текущем.

### D2. Лимиты и настройки на аккаунт + МАССОВОЕ задание
- У аккаунта: дневной лимит действий, порог усталости, окна активности (распорядок).
- **Массовое редактирование** в менеджере аккаунтов: выделил N (или всех) → «Задать
  усталость/отдых/лимиты» → применить пачкой. Это прямой запрос владельца.
- Файлы: `src/pages/AccountsPage.tsx` (bulk-панель уже есть — добавить действие),
  `server/accountsMeta.js` / новый роут массового патча.
- Приёмка: выделил всех → задал профиль усталости → у всех применилось.

### D3. Распорядок дня (вероятность привлечения по времени)
- Профиль аккаунта: вероятность быть вызванным по часам (SPEC §4.2). Модуль «бросает
  кубик»: не попал — идёт к следующему. Ночью (2–5) не писать.
- Учитывать часовой пояс из гео прокси.
- Приёмка: ночью аккаунты молчат; днём активность распределена, не залпом.

### D4. Анти-кластер
- Запрет параллельной работы одного аккаунта в N группах одновременно (SPEC §4.4).
- Человеческий темп: пауза «на чтение» перед ответом, время «на набор».
- Гео-разброс: не все через один прокси в одну секунду.
- Приёмка: один аккаунт не пишет в 5 группах разом; интервалы человеческие.

### D5. Оркестрация «по намерению» (крупное, после D1–D4)
- Кампания принимает желание словами → система раскладывает на модули/задачи (SPEC §2.4).
- Это и есть «комбайн, который управляет системой» из звонка.
